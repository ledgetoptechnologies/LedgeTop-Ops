# Native Processing result consumer: integration gates

Processing draft PR #261 defines `GET /ltds/v1/jobs/{jobId}/results`, object streams at `GET /ltds/v1/jobs/{jobId}/results/{objectId}`, and idempotent `POST /ltds/v1/jobs/{jobId}/acceptance`. Its result manifest binds job, generation, environment, pipeline digest, engine versions and object IDs, sizes and hashes. Its acceptance also binds the input manifest digest, a storage receipt ID, accepted object IDs and validation version. Processing draft PR #272 distinguishes retryable `503 result_read_unavailable` from `502 result_read_failed`, which must hold for review. A 200 stream is provisional until its complete length and digest are checked.

Viewer currently has no durable, authenticated mapping from its attempt to the native job ID, generation, environment, input digest and pipeline digest. Existing NodeODM archive receipts and the native acknowledgement experiment are not that mapping. Do not infer these fields from display names, public URLs, a NodeODM task UUID, or a manifest supplied by an untrusted client. The receiver must first obtain a protected, broker-owned mapping from the exact admitted attempt and native submission; changes or ambiguity hold for inspection.

`nativeReferenceProtocolCandidate.js` is a disabled object-level contract validation experiment with a cross-language digest vector and response classification. It is not an HTTP parser: strict bounded wire decoding, duplicate-key rejection, protected endpoint authentication, deadlines, and source identity are still required. `nativeReferenceObjectCandidate.js` can hash and length-check a stream into a caller-provided empty file handle and sync that file; failed bytes are retained and individual chunks are limited to 1 MiB. Its abort checks are cooperative: a blocked iterator, filesystem call or provider that ignores cancellation still needs supervised process containment and an external deadline. It does not establish exclusive ownership, safe directory traversal, durable directory entries, quota reservation, an object receipt, or an acceptance. Both remain unwired.

`nativeReferenceReceiptCandidate.js` adds an opt-in, separate SQLite experiment for an immutable attempt/job/generation/environment/input/pipeline binding and an atomic storage-receipt plus **held-only** acceptance outbox. It rechecks the current task's active attempt inside the receipt transaction, checks the exact manifest and full object list, rejects identity changes and rolls back the receipt if outbox insertion fails. A child-process test kills the process after commit and verifies replay; it does not prove power-loss durability or interruption between the two inserts. The authorizer and durable-storage verifier are injected callbacks, not real authentication or evidence; filesystem verification occurs outside the transaction and is not protected from concurrent writers. The schema and all records remain forgeable by a direct database writer, there is no sender or transition out of held, and this is not a production migration. Exact real binding provenance, directory durability, exclusive writer/storage authority and crash recovery must be implemented and qualified before activation.

`nativeReferenceStorageCandidate.js` and `nativeReferenceConsumerCandidate.js` are disabled Linux experiments that connect synthetic attempt bindings to an immutable pre-stage intent, exclusive new files, stream verification, file and directory sync calls, and the held outbox. Recovery reopens and hashes all expected complete files and holds on a partial, extra or changed file; repeated staging never overwrites bytes. An interrupted partial run is retained; the experiment can journal a fresh, separately named run, verify it and atomically select it with the held receipt. An authorized bounded run listing allows recovery of a completed run after a lost response. It limits each attempt to eight runs and holds when that limit is reached; a per-database, per-path logical reservation charges each run its full manifest size plus conservative per-file and per-directory overhead, and never releases charges. It is not physical disk or inode accounting: other paths, databases, writers and existing unjournaled files are not covered, and the configured SQLite durability and startup census are not attested. It does not reuse partial bytes. A process-death matrix during run registration, writes, directory sync and selection and real power-loss qualification remain outstanding. The directory checks do not establish exclusive authority against ACLs, same-UID processes, privileged writers, or pathname races, and a storage recheck outside the transaction cannot prevent subsequent changes. The SQLite intent and outbox are forgeable by an unrestricted database writer. The prototype does not prove real power-loss recovery or filesystem durability; actual quota reservation, protected result transport, externally enforced timeouts, and qualified writer fences remain required.

`nativeReferenceAcceptanceCandidate.js` is a disabled, synthetic-loopback-only HTTPS sender. It reads the exact held payload from the candidate outbox, checks a trusted test CA, hostname and certificate pin before transmitting the test bearer token, limits response size and elapsed time, retries bounded 500/503 and transport uncertainty with identical bytes, and holds 409 immediately on response headers (including stored-reference inspection), holds a contradictory inspection marker on 200, and holds invalid responses for review. It accepts unknown additive JSON fields and rejects duplicate decoded keys, excessive nesting, and fractional or unsafe job-generation literals; it is not a closed response schema. A synthetic test kills the sending process after the server receives the request and verifies that a new sender replays the same persisted bytes. A 200 with matching job identity, object IDs, receipt ID and canonical receipt digest is only a partial observation: the complete response and job state are not validated, the entry remains held and no data is deleted. Loopback could reach a real service or proxy; the caller-supplied synthetic flag is not an isolation boundary. Never invoke it outside an independently isolated test environment. Production transport, credential provisioning, durable outcome reconciliation, qualified authority/storage fences and retention gates remain unimplemented; acceptance can trigger upstream behavior and must not be enabled merely because the synthetic test passes.

Before any acceptance, implement an attempt-bound consumer that verifies the manifest and all required stream headers against the trusted mapping; writes each object to uniquely created files under an operator-protected NAS destination without following links or overwriting existing bytes; verifies final lengths and SHA-256; fsyncs files and directory entries; and atomically commits a durable immutable storage receipt and exact acceptance outbox entry. A crash, timeout, mismatch, conflicting replay, unavailable trusted mapping or uncertain filesystem state must retain all partial data and hold. The acceptance outbox must retry the exact same receipt ID and payload, reconcile ambiguous responses, and never grant upstream deletion until a separately qualified retention and writer-fencing policy permits it. A committed receipt alone does not prove Viewer derivatives or 3D readiness.

The current manifest check does not bind the engine list and required result roles to the original requested work, and storage alone does not prove that Viewer actually ingested the required products. Both must be checked using independently trustworthy evidence before any real acceptance. Result providers must implement the candidate's mandatory close callback; it is called on success and on all post-open validation or file failures. A provider that hangs in open, read, or close still requires external supervision and deadlines.

`nativeReferenceIngestCandidate.js` is an unwired Linux experiment for exactly one synthetic `odm_archive` and one ODM engine version. It checks the staged bytes and selected held run, then uses the real archive capture, receipt, output discovery, model registration and derivative scheduling code. The native registration path checks the active lease and selected run inside the model transaction, inserts model/version/assets, attempt link and a marker with registration-input, complete model/asset/file/chunk snapshot and archive digests together, and refuses existing versions; the shared upsert path refuses a marked native version. The protection depends on retaining and attesting the marker schema across all writers and releases, and direct database writers remain unconstrained. The synthetic test exercises transaction rollback and actual Viewer ingest without a NodeODM download or fabricated provider observation, but does not prove Processing provenance, completed derivatives, or a durable acceptance. The disabled recovery experiment can resume the earliest post-registration interruption by adopting the exact existing model after rehashing source files and checking the immutable registration and recovery epoch. It refuses to overwrite assets and can reuse only a staged output whose exact output row and sole base component match a transactionally committed output digest; existing derivative records hold. It does not prove producer identity or lock the filesystem; later interruption recovery is not implemented. The extended marker schema deliberately fails closed on older candidate tables and requires a reviewed, non-destructive migration. Existing archive extraction and promotion are not qualified for power-loss durability; data and directory sync barriers, restart matrix, real trusted identity, requested-engine closure and physical writer fencing remain release gates. Other native roles and combined/Treedar results require separate integration. Old prototype databases missing new schema deliberately fail closed; any future migration must inventory and account for retained runs.

The candidate also binds later attempt-result, model-output, measurement-evidence provenance and derivative/readiness writes to the original active lease generation and selected run. Before a registration marker exists, the provenance check instead requires the original active lease, selected run and empty result link, allowing pre-registration recovery. A same-owner lease reacquisition test holds stale-generation and unguarded competing writes. These checks do not fence direct database access, arbitrary older application versions or other unreviewed writers, and they do not yet recover a partially completed registration.

The disabled expansion reservation experiment checks actual Linux free bytes and inodes on the observed models device and conservatively retains a per-database reservation for extraction and spool work, including on retry. It is not a qualified device-wide reservation: other databases, paths, users, ordinary Viewer jobs and OS processes do not participate; inode and metadata allowances are estimates; previously materialized files can be double-counted; and there is no safe release, startup census or power-loss qualification. The configured reserve and inode floors are rechecked on retries. Do not treat the experiment as proof that a production device has enough space.

`nativeReferenceProviderAuthCandidate.js` demonstrates loading an environment-bound HTTPS origin and secret reference on each use and holding if the configuration or credential revision changes during resolution. Its authorizer, secret store and invocation are injected test seams. It does not enforce transport origin, certificate/hostname checks, redirect policy or revocation during an in-flight request. The proposed receipt ID/digest response is not yet a deployed contract; missing or mismatched fields hold. Processing currently defines separate environment tokens covering all Viewer operations, without overlap rotation; the actual trusted issuer, transport, endpoint, secret access and rotation policy must be qualified before connection or activation.

The existing NodeODM path remains supported and unchanged. No production consumer, outbox migration, provider network call, deletion, production configuration or activation is included in this plan. Processing owns the protocol and proxy; coordinate contract changes before activation. Both projects must qualify the protected transport, trusted issuer, real storage topology, writer exclusion, disk capacity, process/power-loss recovery and end-to-end behavior before enabling native transfer.

`nativeReferenceRecoveryCandidate.js` prepares an unwired recovery epoch for the earliest interruption after model registration, before derivative records exist; an exact staged output and a matching committed explicit-unit evidence set may be reused. It rehashes the staged object, verifies the extracted archive, compares the recorded model and archive digests, then records an immutable recovery-epoch digest under the current active lease; exact replay is tested after a killed process. In isolated tests, the candidate can use that epoch to adopt only the identical registered model and continue to derivative scheduling. It holds changed files or output metadata, conflicting epochs, advanced state, stale leases, unmarked or conflicting unit evidence and any existing derivative jobs. Explicit source-unit evidence can be re-inspected and replayed only when the exact candidate and stored rows match a fenced unit-commit marker; other producer/staff evidence remains held. Source verification happens outside the database transaction, authorizers are synthetic, filesystem and writer fencing are absent, and later interruption points remain unsupported; the epoch is not production authority.

`nativeReferenceDerivativeReceiptInspectionCandidate.js` is a disabled, read-only database evidence experiment. Under one SQLite transaction it attests the candidate intent and receipt schemas and matches a completed job to its exact intent, completion receipt and reconciled resolution, including the readiness marker when applicable. Its optional activation-bound mode also attests the reference schemas, matches the current attempt, registration and activation identities, and recomputes the entire saved derivative plan before accepting a job as a member. It returns evidence only; it does not inspect generated files, constrain other writers, or permit recovery or acceptance. Missing or inconsistent evidence holds. An unrestricted database writer can forge these records, and a real storage and writer authority remains necessary.

`nativeReferenceDerivativeFilesCandidate.js` is a disabled Linux observation for completed EPT and mesh-tiles jobs only. It checks the registered asset, journal, output component and canonical file inventory against activation-bound receipt evidence, hashes the on-disk tree, rejects changed, missing or extra files and rechecks the database evidence. Hashing opens files without following their final symlink, requires single-link regular files, and checks file and directory identities before and after reading; a process-death test rechecks the same evidence from another process. It has caller-set byte and fixed entry limits. The traversal and checks are not atomic with each other or with filesystem/database writers, ancestor path checks remain vulnerable to replacement races, and hashing does not establish durable storage, authenticated provenance, EPT or 3D Tiles semantic validity, or writer fencing. It cannot adopt, publish, send acceptance or release a hold; `lod_audit` and unregistered or incomplete derivatives remain unsupported.

`nativeReferenceDerivativeSetCandidate.js` is an unwired observation of a mixed derivative set: at least one completed job must have activation-bound file evidence, every other job must either have equivalent evidence or match the initial pending-row shape without an intent, receipt or resolution, and job/journal rows must be unchanged across observation. The attempt state and completed readiness receipts must also agree with whether work remains pending. It holds leased, retried, failed, cancelled and unreceipted jobs. A pending row's shape does not prove its prior history, storage isolation or that its reserved capacity was never changed. Checks across jobs are not atomic and can race; the result is not a recovery epoch, authorization, publication, or acceptance and does not release any hold.

The participating repository worker now excludes attempts recorded in `native_reference_model_registration_candidate` from derivative claiming and timeout terminalization, ahead of query limits; unrelated work remains eligible. It holds if other known reference tables exist without the registration table. Synthetic tests run the real derivative-worker entry point in two successive processes, including after the real Viewer ingest of a synthetic ODM archive, and check that its native jobs stay pending. This is a deliberate hold while native writer authority is unqualified, including when the optional derivative-intent guard is disabled. Existing leased processes, older images, direct SQL writers, schema removal and code paths outside these repository methods are not fenced by this filter. An activation or recovery path must not rely on it as exclusive writer authority.

The synthetic archive used in that ingest includes EPT, textured OBJ/MTL/texture, GLB and mesh 3D Tiles but no point-cloud 3D Tiles. With `3d-tiles` explicitly requested, ingest reaches held derivative scheduling and reports the missing point-cloud tiles as a nonterminal archive notice. This establishes Viewer behavior for that fixture only; the Viewer-generated required mesh derivative has not run, and the reported historical 20-photo failure and its effect on upstream ODM completion remain unverified until its exact log and job are identified.

The staged-output digest is recorded atomically with native output registration and rechecked on subsequent guarded writes. This prevents a participating writer from silently changing the output after an epoch was prepared; it does not prevent an unrestricted database writer or a filesystem writer from changing both evidence and data. A disabled activation marker records both the exact initial pending-state digest and a separate immutable job/request/input identity plan. The plan stays stable when jobs progress; the candidate currently recognizes only the exact still-unclaimed state after process death without enqueueing duplicates. That recognition is a point-in-time observation, not a lease or proof of processing. Claimed/changed jobs, advanced state, and non-explicit unit evidence remain held.

`nativeReferenceBoundSenderCandidate.js` composes the environment/secret-reference check with the loopback-only sender. It anchors origin and exact payload across bounded retries, re-resolves credentials each attempt, rejects revision rollback and same-revision token changes within that invocation, and supplies the configured HTTP Host. An append-only non-secret revision ledger additionally tracks observed high-water marks by local provider ID and environment and fixes the origin/secret-reference identity for each revision across job bindings and process reopen. It does not establish stable provider lineage, immutable secret versions, ordering of concurrent sends, resistance to database rollback, in-flight revocation, a trusted secret store, or a production endpoint. Revision scope and non-reuse remain a provisioning contract to qualify with Processing. The joined Processing rehearsal used the earlier low-level sender; this wrapper has only synthetic tests and remains unwired.

`upgradeEmpty46f` is an opt-in, atomic metadata-only upgrade for the exact candidate schema fingerprint from Viewer commit 46f34717 and only when every old candidate table is empty. The separate disabled `upgradeCapacityOnly46f` experiment accepts that exact schema only when its capacity-limit settings are valid and every other candidate table is empty; it preserves those settings and creates the additional empty tables transactionally. Any recorded attempt, run, reservation, receipt or altered schema holds without mutation. Neither experiment inspects or removes files, proves there are no unjournaled files, qualifies activation, or establishes writer isolation. Other historical schemas and databases with recorded work need a separately reviewed migration.

Disposable container tests demonstrate that distinct synthetic UIDs cannot traverse or alter an isolated staged file, and kernel-limited fresh tmpfs mounts retain existing/partial data on byte or inode exhaustion. The quota test intentionally fills and leaves its test mounts until the operator verifies container and mount teardown; its in-container checks do not prove mount ownership. These tests are not evidence of production host isolation, complete broker mediation, real volume quota, or power-loss durability.
