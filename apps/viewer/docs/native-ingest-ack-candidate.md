# Disabled local ingestion evidence candidate

`nativeIngestAckCandidate` is an explicit-opt-in local experiment with a test-only schema. It has no HTTP route, coordinator transport, production migration, automatic worker, deletion, or cleanup authority. It does not implement the proposed coordinator acknowledgement contract.

Before persisting an intent, the candidate requires an active `ready_for_review` Viewer attempt, matching active task, provider, ready managed model output and existing verified producer provenance. It checks the expected loopback provider origin, then rereads and verifies the retained extracted archive inventory against Viewer's stored receipt. A second transaction rereads the relevant database identity after that verification and either persists a fresh request/evidence UUID pair or returns the exact prior pair for the same evidence. Changed or missing evidence holds. It records Viewer's historical ZIP digest; rehashing extracted files is not independently rehashing the original ZIP.

The locally generated evidence UUID is **not** an ingestion commit ID. A separate explicitly installed `nativeIngestCommitCandidate` prototype now records a distinct versioned marker inside the actual Viewer transaction that changes an eligible attempt to `ready_for_review`; the local evidence candidate requires and binds that marker. Only attempts inserted after the candidate is installed are eligible. Pre-install attempts, including historical ready rows, hold and are not backfilled. The prototype attests its own tables and triggers, refuses a partial or altered prior installation, and its marker/eligibility rows reject updates or deletes. It has no production migration or automatic installation.

The expected environment and loopback origin are test inputs, not authenticated issuer, coordinator authority or generation. This candidate does not have an authenticated coordinator receipt digest or a cross-system identity contract. It cannot transmit, acknowledge receipt, authorize retention changes, or release any upstream data. Its SQLite triggers assume trusted writers to the same database; a writer able to alter/drop schema, use another database, or write directly to the filesystem is outside the guard. Its SQLite check does not fence direct filesystem writers during or after hashing. Trigger removal, older binaries, migration/downgrade and rollback require an independently enforced writer-exclusion and retained-marker procedure; no automatic rollback or marker removal is provided. Process-death tests do not qualify filesystem power-loss durability. The current implementation also rehashes the extracted inventory on each preparation and is not qualified for large production datasets.

**Blocking finding:** ordinary SQL can directly insert a fabricated eligibility row and marker, including for a historical attempt; the update/delete triggers do not prove that an inserted row came from the readiness transition. A synthetic characterization test demonstrates this. Until all database writers are independently isolated and authorized, the marker is not trustworthy provenance and must not be sent as an ingestion acknowledgement or used for cleanup. New prototype IDs use canonical version-4 UUID spelling; the spelling alone supplies no authentication or wire qualification.

The synthetic tests use real Viewer repository rows and a small local archive inventory. They hold before readiness and on changed bytes; test both the direct ingest readiness path and final-derivative readiness path; kill a process before and after commit; verify rollback, duplicate transition behavior and marker persistence; hold pre-install rows and partial schemas; and verify stable local evidence IDs after reopening the database. They do not exercise lost network replies, an actual coordinator, external writer exclusion, filesystem power loss or a production acknowledgement.
