# Legacy ingest retry: release and rollback gates

Status: candidate only. Do not deploy until the installed Viewer API and worker revisions, migration level, worker topology, active leases, filesystem behavior and ownership are verified. Migration 41 adds `ingest_publication_intents`; an older worker does not honor this publication fence. An image rollback alone is not a safe rollback.

Before a release or rollback, the operator must stop new admissions and quiesce **all** API/worker writers and cleaners that can touch the shared database or model storage. Prove that old processes and in-flight writers have exited, not merely that their leases expired. Preserve a consistent database backup and the exact source, result, spool and output trees, along with journal/intent and receipt state. Never remove an intent, spool or unreceipted destination to make rollback succeed.

Inventory nonempty state: pending and leased jobs and their attempt identities, lease owners and generations; publication intents; archive receipts; final destinations; and partial or unregistered spools. Reconcile each case using a reviewed, tested procedure. Hold ambiguous destinations and live/uncertain writers for operator review. Restore traffic only after one compatible writer version is active, its authority is established, and queued jobs and accepted outputs have been checked. If that cannot be established, leave writes stopped and retain all data. Do not restore an old database snapshot over newer accepted work without a separately reviewed data-reconciliation plan.

Required evidence before release includes a representative nonempty upgrade and rollback across actual API and worker versions and storage mounts, stale-writer and old-binary fencing, power-loss ordering of SQLite and filesystem operations, and recovery for every publication/receipt boundary. The in-memory migration test demonstrates only that migration 41 preserves synthetic pre-existing pending and leased rows; it is not rollback, deployment topology, or durability proof. Existing Linux-only synthetic retry and crash tests likewise do not establish production mount behavior. A crash after destination promotion but before receipt is deliberately held, not automatically recovered.

Generation checks cover participating ingest heartbeat, failure, completion, model registration and evidence paths. Registration now commits its model, attempt link and output together under one shared SQLite write transaction; an injected output failure exercises rollback. A two-connection synthetic test holds a write lock until the old lease expires, verifies that the waiting worker cannot renew it, then checks same-owner reclaim and cancellation. Additional checks immediately before transaction completion hold expired work; they cannot prove the wall-clock deadline cannot pass during SQLite COMMIT. Unit-evidence expiry and process death at each registration boundary still need targeted coverage. Old binaries remain outside these checks, and the synthetic tests do not prove production filesystem behavior.
