# Provider submission compatibility and recovery

The Viewer rejects submitted basenames containing quotes, backslashes, or line breaks for every provider. This is a generic NodeODM compatibility change: it prevents the multipart encoder from silently rewriting names that may be referenced by GCP data. A parser-independent, byte-preserving mapping for these names has not been qualified. Original source files are retained.

For a positively identified `ledgetop-processing` coordinator, Viewer additionally checks the coordinator's ASCII basename, length, suffix, and nonempty input rules before task initialization. This does not make LAS/LAZ or other rejected types supported. The current Viewer auxiliary matcher excludes CSV, even when assigned `provider_input`; do not claim CSV end-to-end provider upload support. GCP source CSV discovery/import is a separate workflow. Generated GCP formats also reject image basenames containing whitespace, even though the coordinator's ordinary filename policy permits spaces.

Provider `imagesCount` is a count, not proof of the uploaded file identities. Resume-by-count assumes a single authorized upstream writer and an unchanged ordered inventory; out-of-band changes or a competing writer invalidate that assumption. Local source files are hashed before submission and their size is checked when opened, but concurrent mutation during or between those steps and upload is not fully fenced. These are qualification and deployment constraints, not guarantees.

The provider can report a queued state both before and after a commit. When initialization, auxiliary upload, commit, or provider identity cannot be safely reconciled, Viewer retains the existing upstream task and source inputs and records an attention warning rather than removing and recreating the task. A running or completed observation can permit a committing task to continue; an ambiguous queued observation cannot. A reviewed recovery procedure is still required for holds that cannot resolve by later observation.
