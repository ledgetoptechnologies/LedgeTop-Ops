# Full-resolution JPG download candidate

Source candidate only. Requests, worker execution and downloads remain separate
gates; `ORTHOPHOTO_JPEG_DOWNLOADS_ENABLED` defaults to false. No deployment,
conversion, cache publication, access grant or native acceptance is established
by these changes.

The existing staff output and Viewer Downloads menus add **Orthophoto
(full-resolution JPG)** beside the original TIFF only when an exact succeeded
JPG queue result matches the current registered orthophoto source. This works
for imported older models as well as processing outputs; no new reconstruction
is requested. Original TIFF products and generic asset publication are unchanged.
The existing frontend product menu consumes the typed descriptor and grant URL.

The succeeded job is the private registry. Public descriptors contain only kind,
label, format, byte size, filename and grant URL. Cache paths, lease tokens,
source hashes and job IDs are withheld. Only the fixed per-operation image.jpg
path can be selected. Arbitrary cache files never become model assets.

Opaque, short-lived download capabilities recheck staff/session/share authority,
the download flag, original ortho eligibility and the exact source/result
fingerprint. Shares restrict the original `ortho` kind; an unknown `orthoJpg`
asset kind cannot bypass allowed-view restrictions. Each resumed request checks
authorization again, and the sender checks once more after integrity work.
Viewer sessions retain their existing local revocation/version checks; direct
client-share tokens retain their upstream source-authorization check. This
change does not make those two authorization mechanisms equivalent.

The Linux UID568 sender pins private cache directories and the original file
descriptor with no-follow opens, verifies the full SHA-256 with a reused 1MiB
buffer, and serves HEAD, full and single-range requests through the same held
descriptor. It never buffers the complete image. Across factory instances there
are at most two active sends in one Node process. A descriptor-close failure
halts further sends until owner intervention. These limits are per process;
multiple server replicas require separate deployment sizing. Every request
rehashes the file, including HEAD and ranges, which trades disk IO for integrity.
Successful product files must be immutable to other workloads: hashing and
timestamps do not defeat a hostile concurrent same-inode writer.

## Source validation

Run serially with an existing dependency installation:

```
node --max-old-space-size=128 --test --test-concurrency=1 test/orthophoto-jpeg-products.test.js test/orthophoto-jpeg-download.test.js test/orthophoto-jpeg-routes.test.js
```

Seventeen checks cover registry selection, range parsing, inert construction,
SQLite-backed HTTP menus and capabilities, source/result substitution,
disabled downloads, staff/output withdrawal, current Viewer version and
permissions, share restrictions, and revocation during simulated integrity work.
Cloned-share snapshot checks cover upstream authorization waits, including the
final post-integrity check; the inherited shared authorization path now refreshes
share/model state and rejects a changed source binding after that wait.
The HTTP tests substitute the whole sender; they prove no Linux filesystem,
real image bytes, physical descriptor closure or deployed resource behavior.

## Required before enabling

- Independently review the exact source candidate and its dependency stack.
- Qualify the actual Linux UID568 sender with fixed cache ownership/modes,
  HEAD/ranges, inode/path substitution, concurrent requests, disconnects and
  descriptor cleanup on the admitted server, without changing retained data.
- Qualify the real converter/encoder image, full-resolution pixels and image
  fidelity, private disk reservation, worker cleanup and restart behavior.
- Verify installed staff and authenticated-client menus and downloads, including
  source withdrawal, renewal/revocation and denied/resumed requests.
- Validate staging before any separately coordinated production activation.

No JPG job is generated by opening a menu or requesting a download grant. The
existing staff queue-request API is still a separate source candidate. Generation
UI and service-entry/image qualification remain outstanding.
