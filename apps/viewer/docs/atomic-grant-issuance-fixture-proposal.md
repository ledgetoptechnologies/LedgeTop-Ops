# Atomic source-grant persistence: isolated fixture proposal

Status: synthetic experiment only, not an issuer, migration, durable outbox, authenticated ACK, or production route. The existing broker owns a separate SQLite database and starts its own transaction; the Viewer journal uses another database. Neither a second commit nor a post-mint callback makes mint plus encrypted persistence atomic.

Proposed integration requires a jointly reviewed single storage-owner transaction that reserves an immutable operation ID, creates the real broker grant, encrypts its exact canonical bytes, and commits the grant's authorization/ledger and ciphertext together before exposing a response. Establish the existing real broker's quota and source-binding checks inside that same boundary. Use a versioned AEAD envelope with key ID, unique nonce per key, and associated data binding environment, attempt, job/generation, reservation, manifest and ordered object IDs. Nonce generation, uniqueness, collision retry, key rotation, backup, secret distribution, retention and rollback detection need independently qualified designs. Missing or corrupt key/ciphertext, unknown commit, changed intent, and uncertain POST remain held; never infer absence from a missing row after rollback or restore, automatically remint, or delete data. A process restart, network timeout, or lease expiry is not a physical writer fence.

The test helper demonstrates only same-database SQLite transaction structure with synthetic AES-GCM and caller-supplied keys. File-backed tests close and reopen the database, test rollback and a lost-response simulation, and confirm key/binding/ciphertext mismatch and uncertain sends remain held. This is not an actual process-kill, power-loss, uncertain-commit, storage rollback, key-rotation, or nonce-history proof. A missing record after a database restore is not evidence that mint never committed; a trusted external lineage/rollback authority is required and is not implemented. The fixture retains a synthetic test directory for inspection.

The fixture includes version and key ID in AEAD associated data, and models one immutable key ID per distinct key material within its SQLite database. The synthetic HMAC key fingerprint and local uniqueness constraint are test conveniences, not an approved production key registry: they do not prevent aliases or nonce reuse in other databases, after rollback, or under independently provisioned keys. Production must define a protected global key-material identity and durable nonce allocation across all issuers, copies, rotations and restores before use.

It is not integrated with the existing broker and provides no authenticated ACK, recovery authority, nonce history across restore, NAS source pin, access control, real physical budget, or sender fencing. No fake fixture result may authorize a live transfer. Production remains hard-disabled until those components and their schemas, migration and paired contracts are reviewed and proved independently. Raw Emlid CSVs are permanently retained.

## Scoped integration boundary and migration plan

The existing `ReferenceTransferBroker` creates and owns a separate database connection, checks an exact broker-specific schema and starts `BEGIN IMMEDIATE` within `mintGrant`. The Viewer journal also owns its connection and transaction. Passing the same pathname or attaching databases does not make these independently committing APIs atomic, and the existing broker's startup schema inspection rejects unreviewed changes. A callback after `mintGrant` leaves the prohibited crash gap. Do not point either existing owner at the other's database or change schema/activation by stealth.

A reviewed future migration must select one authoritative transactional database and migrate its broker quota, grant authorization, immutable operation intent and encrypted envelope as a coordinated unit; validate legacy rows and define forward/rollback compatibility and collision ownership before allocating a migration number. A storage-owner `atomicMintAndSeal` operation must perform the real broker's capability, file and reservation checks inside that transaction, return only after durable commit, and resolve ambiguous outcomes by immutable operation ID against independently protected lineage. Exact replay must recover the original encrypted bytes; missing/changed keys, unknown commit, divergent state, or rollback must hold. Production secret provisioning, authorized caller, receiver ACK, NAS source/writer/purge fence, physical accounting and v1 compatibility are separate prerequisites.

### Candidate owner comparison

Processing's read-only host check on 2026-11-02 reported cluster `.89` root
with about 111 GiB free of 295 GiB and 629.51 GiB unallocated in its volume
group; main `.88` had about 1.4 TiB free of 1.8 TiB on the NodeODM data
filesystem. The synthetic provider policy routes large jobs to main; this is a
reasonable planning constraint for roughly 50 GB of source data, not a live
capacity reservation. Recheck actual target mounts, expansion/intermediate
needs, retained copies and concurrent reservations immediately before admitting
work. Unallocated volume-group capacity is not usable filesystem space until
an operator provisions it; no resizing or runtime change is included here.

Processing also reports a read-only 2026-11-02 observation that the `.89`
prototype has `PROCESSING_VIEWER_MAX_INPUT_BYTES=21474836480` (20 GiB) and an
archive cap of 107374182400 bytes (100 GiB). The estimated 50 GB photo dataset
exceeds that current intake cap. Preserve the deployed settings until the
NAS-backed queue, capacity admission and retained-copy budgets are designed;
raising the cap alone would put the larger source workload on cluster-local
spool. Recheck actual deployed configuration before any future admission.

Prefer the **existing broker database as the candidate issuance owner**, contingent on the changes and proofs below. Its existing `mintGrant` transaction already commits the grant row and job usage ledger together, so adding a reviewed broker-side operation/intent and encrypted envelope in that same transaction can avoid moving authorization and accounting into the Viewer journal. The Viewer journal should first durably bind a stable operation ID, attempt, exact job/generation, environment, reservation/nonce, manifest and ordered objects, then request the broker-owned operation; it must hold on unknown outcome and reconcile by that same ID. This is a two-system handoff, not a cross-database atomic transaction: a Viewer journal commit is not proof that a broker grant exists, and an absent broker row after rollback/restore is not proof that it never existed.

This is not a property of the current implementation. The existing broker accepts caller-supplied `reservationAvailable`, capabilities, reservation and file paths; its path/source checks happen before its internal transaction. A boolean or matching fingerprint is not a storage-owner, job, reservation, caller or source-custody attestation. Its existing replacement/revocation logic also permits cases beyond one immutable grant per job/reservation; it does not implement the proposed stable operation or encrypted outbox. Before selecting this owner for any real lane, establish an independently authenticated caller and current reservation/claim, an immutable source pin and purge/writer fence, in-transaction exact binding and authorization/usage checks, and a unique non-replaceable operation/reservation identity. Protect the encrypted record, immutable nonce/key identity and grant authorization under the same durable transaction; no network send until commit and independently trusted receiver. Source pin validity must remain enforceable over the transfer, not only at a pre-transaction path scan.

The Viewer-journal-owner alternative would require relocating or transactionally refactoring the broker's own grant table, schema inspection, usage/quota and streaming enforcement into the Viewer database, with wider migration and runtime coupling. Neither option is approved by this comparison. For the broker-owner candidate, explicit migration must preserve existing grant/job accounting and active v1 behavior, reject incompatible or ambiguous legacy rows, allocate reviewed schema identity and offer a tested rollback strategy; do not update #408 or current main implicitly. The broker's endpoint, authentication/issuer authority, encrypted key provisioning, global nonce history, trusted storage/receiver lineage and ACK reconciliation remain unimplemented gates. A separate test-only boundary must fail closed when any is missing.

The `atomic-grant-adapter-boundary.cjs` helper is only a synthetic shape check. It rejects the actual legacy broker rather than calling `mintGrant` as a fallback, and never retries a thrown/unknown result. Its injected fixture outcome is not proof of a transaction, encryption, durable state, authentication or custody. No forward runtime migration or actual broker issuance is implemented here; that remains pending the owner and storage/rollback contract.

`broker-atomic-mint-fixture.cjs` is an additional test-only experiment using the actual legacy broker: it temporarily redirects its inner transaction callback to a synthetic outer SQLite transaction that inserts the encrypted fixture row. Synthetic booleans stand in for verifier and source-pin authority. This demonstrates rollback and close/reopen replay in a disposable test database; monkey-patching a broker transaction is explicitly not a production integration, and the fixture tables are not a guarded forward migration. The legacy broker remains unchanged and production remains disabled. Current source validation, accounting, authenticated ownership and rollback/unknown-commit concerns still apply.

The subsequent synthetic-only broker method `mintGrantAndSealFixture` moves the transaction composition into the broker itself, using the same connection and transaction for the legacy grant/accounting write and encrypted fixture row. Its separate `migrateAtomicGrantFixture` creates an experimental table only when explicitly called with the synthetic scope. The method is not called by dispatch or a route, and injected verifier/source-pin callbacks are not production trust. This is **not** a guarded forward migration: exact schema inspection, schema version/identity, immutable row and key identity enforcement, global nonce management, authorization, active v1 compatibility, failure/rollback lineage, and safe key provisioning are not implemented. The old random grant path cannot be silently adopted; recovery refuses an existing legacy grant without recoverable token. Neither test fixture method may be enabled in production.

The synthetic delivery row records a sender generation and prepared/sending/uncertain/acknowledged state. Its ACK method checks the closed six-field Processing ACK against the decrypted canonical grant and requires an injected receiver callback. A matching duplicate ACK is idempotent; mismatches and stale sender generations hold. The callback is not receiver authentication, state rows lack hardened schema guards, and this is not a durable reconciliation protocol or authority. Unknown outcomes do not automatically retry; no sender fencing, restart lineage or authorized status lookup is established.

An additional fixture-only replay experiment permits a newer sender generation to retry the decrypted exact grant against a file-backed synthetic receiver that seals one canonical digest per job and returns an identical ACK on replay. Both databases are closed and reopened. An injected receiver clock demonstrates that an already-sealed exact grant returns its stored ACK after expiry, while a never-sealed expired grant is held. This models the receiver's ordering, not an actual Processing store, authenticated endpoint, process crash or production durability proof. A generation counter does not fence an old sender. The experiment does not qualify real concurrent POSTs, remote restore/rollback, expiry races, source custody or any production retry.

The synthetic reservation and pin callbacks are called inside the broker transaction, and the binding refuses extra keys. This narrows a database check race only. A callback boolean is not immutable authority, and the transaction does not freeze NAS bytes or exclude independent writers or purge paths; a separately enforced source pin and writer/purge fence remain mandatory.

## Actual storage-owner gate

Uploads finalize through a queued Viewer dataset operation and managed/adopted dataset files. The database manifest identifies recorded files but does not fence old writers, NAS clients, aliases or purge. The ingest worker captures and hashes a provider archive and can reverify an expanded directory during recovery; a receipt in the database alone is not a current physical custody check. The reference broker has its own SQLite owner and an unmounted synthetic method; its `source` checks path containment before its grant transaction. The reference result bridge is unmounted and takes injected authority and ingestion functions. There is no qualified NAS accepted-copy receipt/ACK endpoint in this candidate.

The minimum missing owner-side component is an independently authenticated storage-owner service with a stable, durable dataset/snapshot identity and pin, exact object closure, current receiver/issuer identity, and enforcement excluding writers and purge paths throughout use. It needs durable operation lookup and protected rollback/restore lineage; hold unknown results. Snapshot/hold-based authority is only a candidate until actual mount boundaries, lifecycle, old handles, external administrators and capacity are verified. An immutable database record or `verify() => true` callback cannot supply those guarantees.

TrueNAS 25.10 owner-service research from the Processing chat reports snapshot create/hold/release require `SNAPSHOT_WRITE`, with method-level privileges and no documented per-dataset role in the API schema. Reverify against the installed version before implementation; do not assume the NAS role limits a credential to a dataset. A narrowly scoped storage-owner service must enforce an exact configured dataset and snapshot-name allowlist itself, keep its credential only on the NAS/storage-owner host, and use HTTPS. The researched release method removes all tags, so the proposed lifecycle needs one uniquely named job snapshot and one owner, with explicit verified release semantics; never remove another holder's protection. Whether to use a dedicated queue dataset or snapshot existing Viewer storage remains an owner decision. No TrueNAS configuration, credential creation, or live snapshot is included in this proposal.

For isolated candidate design only, assume a dedicated processing-spool dataset separate from Viewer cache/results. `referenceSnapshotOwnerCandidate` records a closed synthetic source intent before modeled TrueNAS 25.10 `pool.snapshot.create`, `pool.snapshot.hold`, and `pool.snapshot.query` calls; it records unknown outcomes before network mutations and refuses automatic retries after ambiguity. It derives the snapshot name from the exact canonical intent under one configured dataset. Per-object byte counts and their aggregate must remain within JavaScript's safe-integer range before the intent is persisted. An observed hold returns no pin receipt: current code does not verify snapshot bytes, source closure, host mount identity, physical immutability, issuer identity or rollback lineage. It cannot release holds. Its table is test-only, not a hardened forward migration; in-memory tests plus one file-backed close/reopen test and an injected client are not a live TrueNAS service or process-crash proof.

Proposed immutable owner receipt fields, **not an agreed wire schema**, are version, receipt and operation IDs, issuer and authenticated host/ledger epoch, environment, attempt/job/generation, exact input-manifest digest and ordered object IDs/sizes/hashes, dataset and snapshot immutable identity/creation transaction group, source-closure digest, hold identity, observation time, retention policy and issuer signature. Pair exact canonical bytes and version/fingerprint with Processing before consuming it. The real host component must validate staged bytes and mount boundaries under a real exclusive pin, authenticate the requester and issuer, use durable guarded migrations, reconcile unknown calls without adopting an unrelated snapshot, and independently prove lifecycle/rollback/release authority. This candidate neither signs nor emits that receipt.

`referenceStorageOwnerGate.issueAtomicGrant` is an intentionally closed API seam: it always reports authority unavailable, ignores injected callbacks, and is not mounted. No production forward schema migration can safely encode the required authority until the storage owner and its authenticated receipt/operation semantics are agreed. The experimental fixture migration remains synthetic and must not be treated as such a migration. Once the owner exists, pin its identity and exact signed/current intent into a reviewed broker-database migration that commits the immutable operation, grant, usage and encrypted exact bytes in one transaction; verify actual owner-side fencing before and throughout delivery, add durable receipt/ACK and separate cleanup, and retain raw CSVs permanently. Existing v1 and the hard-disabled worker lane stay unchanged.
