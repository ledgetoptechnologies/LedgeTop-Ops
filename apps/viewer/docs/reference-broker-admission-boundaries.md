# Reference broker admission boundaries: synthetic investigation

Processing's current source client requests one whole object per GET and expects 200, the exact object length and SHA-256. The unmounted Viewer broker candidate defaults to a 16,777,216-byte maximum response, 67,108,864 concurrent reserved bytes, and 100 requests per job. A 10,000-photo manifest requires at least 10,000 GETs before any retries; a photo over 16 MiB is refused under the default. An approximately 50 GB target is not an admission guarantee. Concurrency, per-object size, cumulative source bytes, attempts and retry allowance must all be negotiated and enforced as a single bounded contract; selecting larger numbers without capacity, reservation and abuse analysis is not sufficient.

The current broker charges a response's full length and one request to durable job usage before opening the source; an abort or failed read does not refund that job charge. Reservations also bind grant and cumulative byte budgets. The attached synthetic tests exercise actual candidate behavior with small temporary files and a sparse oversized file; they do not run 10,000 network requests, validate real NAS capacity, demonstrate crash recovery, or qualify a new budget. A test-only arithmetic boundary highlights that default request capacity is insufficient even when every object is tiny. An approved live design must explicitly decide retry/headroom policy, admission control, expiration and recovery for exhausted or ambiguous grants, object-size and count ceilings, concurrent resource bounds and source custody. Never widen caps silently or mint a new grant to erase previous charges.

The HTTP handler remains unmounted and processing dispatch remains disabled. No TrueNAS directory, mount, policy or deployment is changed.
