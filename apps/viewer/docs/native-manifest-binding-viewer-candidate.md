# Viewer native manifest binding: unwired candidate

This is a test-only, opt-in candidate against Processing #246's proposed identity receipt. Nothing imports it from the Viewer app or worker; it creates no production migration, route, transfer, dispatch, reservation of physical space, or activation switch. Its HTTP transport refuses non-loopback endpoints. A real deployment requires a separately reviewed integration, authenticated transport and migration; do not use this candidate schema against a live database.

The candidate checks canonical manifest bytes against the strict provisional native profile and shared vectors. It generates a 32-byte task capability and stores it with the existing AES-GCM vault, using an attempt/task/environment/loopback-authority-specific associated-data context before sending anything. It records a durable intent, reserves using the same capability on exact retry, persists a binding phase before the bind request, and stores only an exact validated receipt. If the bind response is lost or the process dies, recovery requests status using the same capability and test environment token; absent, inaccessible, malformed, mismatched or otherwise uncertain status holds rather than generating a new capability or repeating a bind. A previously saved receipt is compared field-for-field to the next status. The loopback test does not establish remote server authentication. No capability is returned in results or intentionally logged. Key unavailability, ciphertext tampering and input/identity changes hold; this candidate intentionally supplies no delete, capability rotation, or cancellation action.

The receipt is identity metadata only. Its `bindingId` is an unkeyed consistency digest, not a signature or user identity; environment credentials do not identify a distinct person. `acceptedInputLimit` is historical policy, not available space, a reservation, or permission to upload. `capacityReady` must remain false. Viewer-local initialization generation and coordinator generation are distinct. Route availability must never be inferred from engine name or an unrelated capability.

The current candidate contract places the environment token in the request query string. Even though this loopback-only client does not intentionally log it, HTTP servers, reverse proxies, tracing, error reporting, or other local diagnostics may record URLs. A remotely authenticated integration must remove or reliably redact query tokens at every logging and tracing boundary, or agree a safer credential transport before use; the present test does not prove that property. Error response bodies are cancelled rather than read. The candidate receipt parser accepts only the nonnegative safe integer lexemes needed by this receipt, rejects malformed UTF-8, lone surrogates and duplicate keys, and still relies on exact field-level receipt validation; it is not a general numeric canonicalization contract.

The synthetic cancellation test proves that a nonsettling body-cancel promise does not block the caller. It does not prove underlying socket or resource closure for every transport, nor bound a custom fetch implementation that ignores abort. The `bindingId` is stored and compared as an opaque correlation value received over the authenticated channel; the client does not independently verify it as a signature.

Before any real integration, review and qualify: persistent schema migrations and backwards compatibility; exact authenticated remote endpoint and capability negotiation; task-capability creation, encryption-key rotation/recovery, retention and explicit cancellation; duplicate/concurrent client execution and stale-worker fencing; complete response verification and process/power-loss recovery; immutable source bytes; exact canonical vectors across languages; and no unintended logs or secret exposure. Bind the canonical task plan, requested options/outputs, and option-catalog evidence as a separate agreed contract before execution: #246 currently binds input identity only. Physical allocation, spool behavior, old-writer exclusion, cross-host filesystem locking and durability, and a separate capacity-ready decision remain open. No production use is authorized by these tests.

The adjacent opt-in `nativePlanCandidate` is also unwired and has only an explicitly installed test schema. It snapshots the task display name and ordered options from the persisted Viewer attempt using the same option enumeration as the existing adapter, plus an explicit output value and catalog digest, into immutable canonical bytes and a domain-separated plan digest. Exact repeats return the same snapshot; changes hold. It matches the shared synthetic plan vectors, including `outputs:null` versus `[]`. The current worker has no persisted output-selection flow, so caller-provided output values and catalog digest are not proof of an authenticated user selection or coordinator-issued evidence. Even for locally representable nonempty options, the builder reports option profile unqualified, engine evidence unavailable, capacity not ready and dispatch not ready. The builder itself cannot execute the plan.

An adjacent explicit-opt-in plan-binding client can POST only an empty-option plan with the known empty-catalog digest to a loopback test endpoint, using the same encrypted task capability and the prior manifest receipt. It persists binding intent before POST, recovers uncertain POST only through status, strictly compares every receipt field, and rechecks the active local attempt, provider, environment, origin, manifest and encrypted-capability context before saving. Unknown or mismatched status holds; no upload or dispatch method exists. Its earlier test-only plan schema has no migration and is rejected rather than silently changed. Loopback requests demonstrate protocol behavior only, not remote authentication, current catalog authority, server-side durability, or production safety.

**Pre-side-effect race; release blocker:** the original local context check and `binding` transition committed before network POST, allowing cancellation or replacement before a remote bind. The test-only plan client now uses a coarse, durable single-database in-flight fence: it transactionally records operation identity before POST, installs database triggers that hold cooperating local context mutations, retains the marker across process death or uncertain replies, and clears it only in the same transaction that stores a verified exact receipt. This prototype serializes all covered work, not just the target task. A separate-process test covers a competing cancellation after a crash. No timer or lease expiry clears it, and no automatic cancellation/revocation resolution is implemented.

This local fence does not prove coordinator-side authorization, prevent old writers using a different database or direct filesystem access, establish authenticated remote transport, or qualify deployed SQLite/filesystem locking. A coordinator can still accept an already-sent POST before revocation; a local cancellation must not be reported complete until the coordinator outcome is reconciled under an agreed v2 protocol. The test-only schema has no production migration or hardened database authorization: a direct SQLite writer can alter or delete the marker or matching-kind state without changing the schema. A status response does not itself prove an earlier POST cannot still commit; a coordinator-side barrier is required. No production POST or automatic cleanup is authorized by the prototype.

Before any production plan POST, design and qualify a durable cross-system fence. At minimum, bind a unique immutable plan/attempt/provider/environment/capability identity and monotonic operation generation to an in-flight intent; require every local cancellation, replacement and relevant context mutation to participate in the same fence, including all older workers and direct writers. The coordinator must atomically validate and consume a corresponding current authorization or epoch before creating its durable binding. Define a cancellation/revocation barrier whose acknowledgment proves whether a competing bind can still commit. Never hold a SQLite write transaction open across an unbounded network call, and never reclaim authorization merely because a lease, timer or process expired: the remote operation may still arrive. If a crash, partition, timeout, or lost response prevents proving which side committed, preserve capability, intent, source and remote data and hold for authenticated reconciliation. A locally generated token or a second local check alone cannot fence a coordinator that does not enforce it. Define explicit operator recovery and rollback rather than silently recreating a binding.

The unwired `nativeEpochReceiptCandidate` checks draft v2 envelope and history consistency only. It requires callers to supply strict nested manifest/plan receipt validators and a persisted expected operation, plan and revoke identity; no such v2 client or durable epoch integration is implemented yet. The separate loopback-only `nativeEpochTransportCandidate` is a test helper, not an authenticated production transport. It sends the environment credential in a header with no query fallback. A synthetic Python/JavaScript replay covered both close outcomes against a SHA-256-verified source archive of Processing commit `95f0de977b28113eb6181c4d44e1bacca07b397f` using that header contract and the local test-state primitive with synthetic context. For the bound case a proxy withheld the coordinator's successful revoke response, the sending process was killed, and a fresh local connection recovered the persisted request and closed status before releasing the marker. It does not exercise real Viewer context, both concurrent coordinator race orderings, or establish a production cancellation barrier. Legacy query-token and proxy logging risks remain. The contract and byte-level fixtures remain provisional.

`nativeEpochStateCandidate` is a separate unwired test primitive that persists a stable operation and a single exact revoke request while holding the local coarse fence. A synthetic test kills the writer immediately after committing that request and recovers it from a fresh database connection; it does not simulate a lost network reply. Its local finish operation checks the expected terminal envelope and nested-receipt callbacks, then atomically saves that envelope and releases the marker. The primitive has no integrated authenticated network client or real context implementation: caller-supplied context and receipt checks are trusted, not authorization. It must not be treated as a complete durable epoch client or production recovery implementation.

The separately tested `nativeEpochViewerContextCandidate` can capture an identity digest from a real active Viewer attempt and immutable manifest/capability record, and verifies the provider is the expected loopback endpoint. It is not yet wired into the state/transport replay or an end-to-end client. Its digest and the SQLite triggers are local consistency aids, not authentication or coordinator-side fencing.

Qualification must exercise cancellation/replacement/provider change at every pre-send, in-flight, remote-commit and local-receipt boundary; delayed packets after revocation; process and host crashes; concurrent old or bypassing writers; stale generation replay; duplicate requests; lost replies; and server cancellation/commit races. Verify that a reported cancellation and a later accepted bind cannot both be treated as valid, and that unresolved cases remain held without deleting or overwriting data. The required authority, revocation and authenticated transport semantics are not implemented by this candidate.

The snapshot candidate requires the exact same SQLite connection used by the processing repository, an explicit expected environment, an active attempt and project, an enabled matching provider, and the bound provider/task/loopback origin. It checks these inside `BEGIN IMMEDIATE`; a synthetic second-connection writer is blocked while that transaction runs. The environment expectation is supplied by the test caller and is not independent authentication. This remains a local single-database test, not proof of deployed or cross-host authority. The test schema has no immutable database triggers, production migration or schema attestation; do not treat it as production protection. Plan bytes can include sensitive task names and option values and must not be logged or broadly dumped. The test-only capability envelope now includes provider identity in its authenticated context; there is no migration for previous candidate-only rows, which must hold rather than be silently reused.
