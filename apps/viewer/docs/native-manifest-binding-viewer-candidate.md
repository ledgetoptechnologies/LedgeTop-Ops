# Viewer native manifest binding: unwired candidate

This is a test-only, opt-in candidate against Processing #246's proposed identity receipt. Nothing imports it from the Viewer app or worker; it creates no production migration, route, transfer, dispatch, reservation of physical space, or activation switch. Its HTTP transport refuses non-loopback endpoints. A real deployment requires a separately reviewed integration, authenticated transport and migration; do not use this candidate schema against a live database.

The candidate checks canonical manifest bytes against the strict provisional native profile and shared vectors. It generates a 32-byte task capability and stores it with the existing AES-GCM vault, using an attempt/task/environment/loopback-authority-specific associated-data context before sending anything. It records a durable intent, reserves using the same capability on exact retry, persists a binding phase before the bind request, and stores only an exact validated receipt. If the bind response is lost or the process dies, recovery requests status using the same capability and test environment token; absent, inaccessible, malformed, mismatched or otherwise uncertain status holds rather than generating a new capability or repeating a bind. A previously saved receipt is compared field-for-field to the next status. The loopback test does not establish remote server authentication. No capability is returned in results or intentionally logged. Key unavailability, ciphertext tampering and input/identity changes hold; this candidate intentionally supplies no delete, capability rotation, or cancellation action.

The receipt is identity metadata only. Its `bindingId` is an unkeyed consistency digest, not a signature or user identity; environment credentials do not identify a distinct person. `acceptedInputLimit` is historical policy, not available space, a reservation, or permission to upload. `capacityReady` must remain false. Viewer-local initialization generation and coordinator generation are distinct. Route availability must never be inferred from engine name or an unrelated capability.

The current candidate contract places the environment token in the request query string. Even though this loopback-only client does not intentionally log it, HTTP servers, reverse proxies, tracing, error reporting, or other local diagnostics may record URLs. A remotely authenticated integration must remove or reliably redact query tokens at every logging and tracing boundary, or agree a safer credential transport before use; the present test does not prove that property. Error response bodies are cancelled rather than read. The candidate receipt parser accepts only the nonnegative safe integer lexemes needed by this receipt, rejects malformed UTF-8, lone surrogates and duplicate keys, and still relies on exact field-level receipt validation; it is not a general numeric canonicalization contract.

Before any real integration, review and qualify: persistent schema migrations and backwards compatibility; exact authenticated remote endpoint and capability negotiation; task-capability creation, encryption-key rotation/recovery, retention and explicit cancellation; duplicate/concurrent client execution and stale-worker fencing; complete response verification and process/power-loss recovery; immutable source bytes; exact canonical vectors across languages; and no unintended logs or secret exposure. Bind the canonical task plan, requested options/outputs, and option-catalog evidence as a separate agreed contract before execution: #246 currently binds input identity only. Physical allocation, spool behavior, old-writer exclusion, cross-host filesystem locking and durability, and a separate capacity-ready decision remain open. No production use is authorized by these tests.
