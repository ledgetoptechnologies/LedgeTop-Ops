# TreeDar project provenance: synthetic contract proposal

This is a design and fixture only. It changes no runtime, schema, UI, provider, or processing behavior. TreeDar remains unavailable until an authenticated, project-scoped immutable asset/receipt resolver and a durable acceptance path exist and are reviewed. A receipt ID or evidence supplied by a caller is not evidence of source authenticity. File extensions, media types and LAS headers alone do not prove a genuine sensor-derived LiDAR source. A trusted verifier must bind provenance to exact selected project assets and content hashes; independent worker validation of contents, CRS, units and usable ground returns remains necessary.

The synthetic vectors specify a proposed admission boundary for explicit opt-in: an advertised current capability; a typed request bound to a project, immutable asset IDs and SHA-256 hashes; trusted resolver evidence for the same project, IDs, hashes and receipt; and an affirmative genuine sensor-origin finding excluding photogrammetry-derived clouds. Missing, stale, untrusted, cross-project, changed, or inconclusive evidence must reject, never silently downgrade to ODM. Gaussian splat remains disabled. These vectors are deliberately abstract and are not a wire contract or a functioning receipt issuer. The exact evidence schema, issuer identity, revocation and freshness policy, asset authorization, durable intent and recovery semantics require joint review.

`test/treedar-project-provenance-vectors.test.js` is a fixture-only policy oracle, not an integration test or a source of trust. Its supplied evidence represents an authenticated resolver result only in the synthetic test. Passing it does not make Processing or Viewer capable of executing TreeDar. Cross-repository consumers must adopt the same vectors and verify their own real trust boundary before claiming interoperability.

Keep raw source assets and survey CSVs intact. No real job submission, deployment or runtime activation is included. Existing reference-v1 grant outbox, sender fencing and restart/acknowledgement recovery remain separate unresolved gates.
