# Proposed Viewer–Processing input manifest handshake

Status: proposal for joint review; no wire protocol or disk-reservation behavior is implemented here. Do not send new fields until both sides agree on capability negotiation, the exact contract, and failure semantics.

Processing's initial review supports reusing its reference-v1 manifest where practical, with a stricter native ODM profile. The reference currently limits a manifest to **10,000 total objects**: 10,000 photos plus a generated GCP file exceeds that limit. Do not silently increase the limit or claim that combination is supported. The JavaScript and Python validators have differences; agreement and shared cross-language vectors are required before treating their acceptance sets as equivalent.

## Existing boundary

Viewer records an ordered input inventory and initialization intent locally. The current NodeODM-compatible initialization sends the assigned task UUID, display name, and options; it does not send or receive a coordinator-bound input manifest. Local inventory entries contain source-relative paths, whereas the upload uses basenames. Generated `gcp_list.txt` replaces any selected file with that name. The actual transmitted inventory must therefore be constructed after file-role filtering and GCP replacement, using precisely the names and bytes that will be uploaded.

The coordinator's advertised input and request limits are admission hints, not reservations. Its multipart handling can temporarily spool parts before copying them into separate destination inodes, so raw input bytes alone do not establish peak free-space requirements. A manifest is an input-identity contract; it is not physical allocation, host fencing, immutable source storage, or a guarantee that capacity will remain available.

## Contract to agree

1. The coordinator advertises an explicit versioned capability with supported size and file-count limits, manifest endpoint/encoding, and receipt/status semantics. Viewer must not infer support from engine name, version, or an unrelated limit. Generic NodeODM and coordinators without this capability retain their existing protocol and are shown as lacking manifest assurance. Once a task has been bound under the new protocol, do not silently downgrade or recreate it through the legacy path.
2. The declaration identifies the assigned provider task UUID, a Viewer-side attempt and initialization identity suitable for idempotency, and an ordered list of the exact transmitted basenames, byte sizes, and SHA-256 digests. The list includes generated GCP content and excludes administrative/source-only files. Reject incompatible names and duplicate coordinator-normalized basenames; do not rewrite names. Check each number, aggregate, item count, and serialized size for negotiated bounds without integer overflow. Avoid including client paths, credentials, or unneeded metadata.
3. Agree on one versioned, byte-exact canonical encoding and digest algorithm, with cross-language conformance vectors. Define JSON/Unicode handling, key and list ordering, duplicate keys, integer representation, hex case, maximum lengths, and rejection of unknown fields. Do not reuse Viewer's existing local manifest digest without verifying that both sides hash exactly the same transmitted inventory representation.
4. The coordinator durably binds the accepted canonical digest and inventory to the task UUID and its own newly allocated generation before upload acceptance. Its acknowledgment returns the protocol version, UUID, generation, and digest. Viewer records the acknowledgment against its existing initialization intent before proceeding. The precise endpoint, representation, and generation ownership remain open for coordinator review.
5. A repeated declaration for the same live task/generation succeeds idempotently only for the identical digest and inventory. Mismatched declarations, reused UUIDs, unknown generations, or missing durable acknowledgement fail closed without overwriting files or starting work. Lost responses are reconciled by a read-only, authenticated status/receipt query that proves the same UUID, generation, digest, and state; ambiguous observations hold for review. Neither side deletes/recreates a task merely because a reply was lost.
6. Each upload is accepted only for the declared generation and expected basename. Coordinator verifies its actual byte count and digest before marking that entry complete. Replays of identical verified content must have defined idempotent semantics; mismatches and unexpected inputs fail closed and preserve existing verified data. Commit is idempotent and requires the exact declared set, not merely a photo count. Any already-running, completed, failed, or cancelled task is handled explicitly; no ambiguous queued state triggers destructive restart.
7. Capabilities and acknowledgments are authenticated and bound to the configured coordinator identity. Durable records must survive process restarts and have explicit retention, cancellation, generation-reuse, upgrade, and rollback rules. Avoid leaking signed URLs, tokens, source paths, or private file names into broad logs or release records.

## Reference-v1 direction from Processing review

- Candidate manifest fields are the existing reference object's `id`, `revision`, `sha256`, `totalBytes`, `objectCount`, `inputCounts`, and ordered `objects`; object entries include `id`, `name`, `byteSize`, `sha256`, `kind`, and `mediaType`. Compute SHA-256 over compact, sorted-key UTF-8 JSON with literal Unicode, excluding the top-level `sha256` field. The reference prohibits non-finite numbers. These are candidate reuse rules, not an agreement to skip native-profile validation.
- The native profile must require positive object sizes, the intersection of reference and #242 coordinator basename and suffix rules, ODM images and auxiliary inputs only, and `points=0`. Reject unsupported LiDAR instead of advertising it as available. Preserve object order and verify totals and counts against the transmitted inventory. Apply every reference size bound, including request-body limits, unless a separately reviewed protocol revision changes it.
- The candidate flow is capability-negotiated begin/bind/status: the coordinator issues a generation and durably binds UUID, environment and manifest digest; Viewer supplies its attempt identity as an opaque replay key. Manifest acceptance and a later physical-capacity-ready receipt are separate states. Exact-set commit must verify the actual stored hashes and lengths, not `imagesCount` alone.
- Existing coordinator tokens identify an environment, not a distinct principal. Do not describe them as per-user identity or use them to infer independent writer authorization. Same-inode allocation, multipart spool lifecycle, migration, old-writer exclusion, and physical capacity reservation remain unresolved and need their own design and tests.

The **joint candidate**, not an enabled or production-qualified protocol, uses an opaque Viewer attempt-scoped identifier as `manifest.id`, immutable `revision` 1, and deterministic one-based object IDs `o000001`, `o000002`, etc., in the frozen photos-then-auxiliary/GCP transmitted order. This allows Viewer to freeze and hash the inventory before the coordinator assigns a generation. The coordinator separately allocates a positive safe-integer generation and durably binds environment, provider task UUID, generation, manifest id/revision/digest, opaque Viewer attempt replay key, and task capability. The attempt identifier is not a user identity. An exact authenticated replay returns the same binding; a conflict, terminal or reused UUID, missing or uncertain state, or changed inventory holds without reallocation or deletion. Lost acknowledgments must be reconciled to that same binding. Route and uniqueness details, historical retries, generation reuse, and actual physical reservation and fencing remain unqualified.

## Required qualification before rollout

- Independent cross-repository agreement and versioned conformance tests for canonical bytes, hashes, UTF-8, names, numeric overflow, generated GCP, duplicate input, and old-provider fallback.
- Real bounded multipart tests for exact part framing and request caps, mismatched/truncated file bytes, lost init/upload/commit responses, repeated identical requests, concurrent writers and conflicting inventories, cancellation, process death at each persistence boundary, and task/generation reuse.
- Separate, measured admission design for worst-case spool, final copy, archive and filesystem headroom; clarify any reservation ownership, release, crash recovery, and external-writer assumptions. Do not present `statvfs` or a manifest total as guaranteed physical capacity.
- Independent verification of shared-authority topology, cross-process/host fencing, real filesystem locking and fsync/power-loss semantics, and a release/rollback plan that excludes older unfenced workers. These remain separate production gates.

Open questions for Processing: capability and endpoint shape; coordinator-owned generation allocation; canonical serialization and size limits; exact receipt/status fields; byte-stable idempotency rules; disk-admission ownership; retention and upgrade policy; and how failure states are surfaced to the operator.
