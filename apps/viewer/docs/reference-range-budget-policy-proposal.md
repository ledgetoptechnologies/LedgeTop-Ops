# Proposed range and job budget vectors

These vectors are a cross-language review proposal, not a current wire contract or capacity qualification. Their fields are synthetic: an eventual closed, authenticated policy must bind chunk and object limits, immutable job/input identity, request and byte budgets, and policy version to the actual grant and job ledger. Processing currently accepts up to 3× manifest bytes; the proposed 1.5× limit is not in the existing grant. Both sides must agree whether to change that validation or add a distinct signed closed policy field before implementation. Do not silently reinterpret v1.

The proposed plan uses 16 MiB ranges, 256 MiB per object, 10,000 objects, 64 GiB source bytes and a 20,000 base-request ceiling. Current Processing v1 rejects zero-byte manifest objects, so this proposal rejects them too; allowing them would require an explicit separately agreed wire and broker policy. For nonempty objects, base requests sum `ceil(objectBytes/chunkBytes)`; request and byte limits are `ceil(3*x/2)` with safe integer arithmetic, bounded by 30,000 requests and 96 GiB respectively. These values are not validated against real source size distribution, processing expansion, host free space, retry rates, or operational resource limits. Reject inputs outside the policy before transferring; do not silently increase caps.

Initial processing gets one attempt per exact range, with no automatic retries. The broker durably charges each requested range and its full length before streaming, even if the response aborts. After an ambiguous response or worker restart, hold until persisted range and charge state can be reconciled against authenticated broker records. Resume only independently verified persisted bytes at a proven offset; current Processing discards its private part on failure and cannot do this yet. Generation changes, replacement grants and owner changes must retain the cumulative immutable-job/input budget; no remint or reset on uncertainty. The recovery vector only serializes a mock map, not a durable ledger or implementation.

Both sides still need closed policy/receipt formats, authenticated and durable ledgers, range offset persistence and recovery, resource admission, writer fencing, immutable source custody and grant/ACK replay. Tests here do not run real transfer, worker restart, 10,000 requests or production authentication. Existing runtime and configuration remain unchanged.
