# Provisional source spool database hold

Migration 62 and `sourceSpoolHoldCandidate.js` are an unmounted review candidate on top of the #408 draft, which already uses migrations 60 and 61. The number is provisional: verify all other branches and deployed migration identities and rebase or assign a jointly reviewed identity before any activation. Nothing invokes this helper in the application. It never grants admission or copies, seals, releases or deletes source data.

The helper binds the existing active attempt, task, project, managed finalized dataset and manifest in one SQLite transaction, rejects pending dataset operations and known direct dataset/task/project storage mutations or active trash, and makes exact retries idempotent. Candidate triggers block dataset and file metadata changes, direct storage and trash records, active-attempt replacement, and project/task archival and deletion. Task or attempt cancellation may stop work but does not release the hold. There is no release implementation: holds remain retained, and an applied migration would install its triggers automatically even though the helper is unmounted.

Provisional migration 63 adds a distinct copy intent. The unmounted Linux-only `sourceSpoolCopyCandidate.js` attempts to copy actual held dataset records under a configured spool root, verify each file's size and hash, fsync and re-read the destination, and publish a no-replace seal. It records `copying` before filesystem effects; after a failure or restart in that state `inspectSpoolIntent` reports `held_uncertain` and refuses admission. It does not inspect or recover partial files, and automatic replay is unavailable. A crash after seal publication and before the database update also holds. Bounded Linux container tests cover sample copy/readback, symlink and hash rejection, injected ENOSPC and destination corruption, and child termination at selected boundaries. They do not establish power-loss durability, real disk exhaustion, concurrent external mutation, NAS behavior, or complete crash-state recovery. A sealed record is not admission or proof of protected storage, and there is no cleanup or release. The root must be supplied by trusted operator configuration, never a client. Both provisional migrations install automatically if this draft is deployed; do not deploy it.

This is not a complete writer or purge fence. Uncovered effects include already-issued filesystem operations, parent/container mutation plans and aliases, external NAS writers or administrators, direct filesystem paths, destination-root replacement and ownership/mount verification, cancellation/ownership lineage, and older processes lacking the triggers. Existing in-flight filesystem work is not physically fenced by a row. Authenticated coordinator acceptance, grant issuer, range budgets and replay are absent. No production routes or workers may rely on this candidate until those cases and migration/deployment compatibility are resolved. Survey CSV and other raw source data remain retained.

The unmounted `verifyExistingSpool` diagnostic reopens a candidate directory, compares its seal and object list against the held Viewer dataset and rehashes every object. It does not update state, adopt a seal, reserve space, create another generation or authorize admission. Partial, missing, changed and ambiguous directories remain held. Safe retry still needs persistent generation and directory ownership, trusted physical quota/reservation and retention, and a proof that the prior writer and external writers are fenced. Diagnostic readback alone is not that proof.

Provisional migration 64 adds append-only logical generation holds. The unmounted helper charges each new generation's full dataset byte size against a caller-provided logical ceiling and includes all existing initial intents and retained generation holds. Its deterministic directory ID is a reserved label only: no directory identity is established and no copy is allowed. The ceiling is not a trusted physical disk reservation, the helper does not verify source or prior-generation bytes, and no new generation can be accepted or started. Quota policy, root ownership, physical capacity, source revalidation, prior writer fencing and lifecycle release remain prerequisites. Migration 64 also requires branch and deployed-identity reconciliation and must not be deployed as-is.
