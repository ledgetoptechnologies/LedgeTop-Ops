# Viewer ingestion writer boundary: implementation proposal

The current deployment does not have this boundary. Both Viewer API and worker open the same SQLite database directly. Their checked-in configuration uses the same `568:568` identity and writable `/app/storage` bind, which includes the database and its directory. The operator-reported live API and worker database device/inode match, but that observation does not exclude other writers. A process with equivalent database-directory access can replace the database, WAL or SHM, change schema, or insert a fabricated marker. SQLite triggers or a connection-local authorizer cannot stop an old or direct writer with that access. No ingestion acknowledgement or upstream cleanup may depend on the marker under this topology.

## Proposed boundary

Move **all** SQLite write authority to a narrowly privileged database broker, not merely the new marker insert. The API and worker would use separately authenticated, bounded broker methods for their writes and would have no OS-level write access to the database, its parent directory, WAL, SHM, backup/restore paths or equivalent alternate copies. The broker must own those paths under a distinct service identity. Host administrators and any process with root, DAC bypass, broker identity, access to the broker's credential, a second mount, or equivalent storage privilege remain trusted; ordinary Unix permissions do not constrain them. A public network listener, a shared service UID or a marker table alone is not this boundary.

Broker methods must bind the authenticated component and delegated user/tenant authority to an exact operation, attempt, provider task, model version and current lease. Only narrowly defined transactional mutations are exposed; no caller-supplied SQL, arbitrary file paths, direct schema operations or generic marker insert is permitted. The broker itself must implement and validate the readiness transaction and immutable provenance. Authenticate coordinator receipts and service principals separately; Unix peer identity alone does not establish end-user or coordinator authorization. Enforce a separate filesystem boundary for source/output bytes and their publication; a trusted database cannot prove files were not altered by another writer.

The prototype under `test/helpers/native_ingest_broker_fixture.py` is an **isolated proof**, not this service. It uses a Linux Unix socket with `SO_PEERCRED` to distinguish one synthetic client UID, a different database-owning UID, and a narrow `complete` operation. The operation invokes the actual Viewer `completeOutputForReview` method and the opt-in marker trigger on a synthetic database. The opt-in container test demonstrates that two other UIDs, including a stand-in for the current old `568` identity, cannot open the protected database for writing; an unauthorized peer and an unknown operation are refused; a designated peer can complete the actual readiness transaction; and a broker restart replays the same marker. A forced timeout exercises the broker's bounded `Popen` child termination and reaping. Teardown asks each test-owned broker to stop and verifies reported children were reaped before removing temporary state; it retains the directory if cleanup is uncertain. It does not signal a process group by a possibly reused numeric ID.

**Operator prerequisite:** run this only in a disposable network-isolated Docker test container with a read-only root, disposable `/tmp`, bounded resources and the minimum capabilities required for test UID changes and ownership. It additionally requires `VIEWER_BROKER_ISOLATION_TEST=1`, Linux, root inside the container and a `/.dockerenv` marker; that marker is only a mistake guard and does not establish isolation. A broker crash could leave an unreported child: the test retains temporary state unless the broker exits normally after its drained acknowledgement, and the disposable container must be terminated to contain any unreported descendant. Never opt in on the host or against real Viewer storage. The proof described here made no changes to TrueNAS or live data.

The fixture passes the exact request and broker-observed peer UID into the readiness candidate, including lease owner and the complete event. A fault injection closes the connection after commit before returning a reply; a fresh client replays the exact request after a clean broker restart and receives the original marker without another event or audit entry. It rejects an altered replay. This remains a synthetic peer UID with broad access to the operation: a caller-supplied lease owner is not a real per-task credential. The fixture does not prove worker process crashes, broker crashes, real tenant/user authorization, the full API, worker, migrations, model assets, root/host access, malicious broker, denial-of-service, backup/restore or multiple hosts. The opt-in trigger remains forgeable wherever a direct writer retains database access. SO_PEERCRED must be separately validated under the actual container namespaces and UID mappings. No production installation or acknowledgement can rely on this fixture.

A separate file-backed candidate test kills its own transition process immediately after the SQLite commit and before any reply, then starts a fresh process to replay the same receipt and checks one event and one audit entry. This exercises candidate-process crash recovery only; it does not simulate a production worker or the socket broker crashing, their supervisor behavior, or machine power loss.

An independent `nativeReadinessGrantCandidate.js` verifier experiment checks an Ed25519 signed, short-lived grant against a trusted key, issuer and broker-observed peer identity. The grant signs a domain-separated digest of the entire canonical request, using the same digest as the candidate replay receipt, as well as binding peer, attempt, job, project, subject and lease owner. This digest format changed during the experiment; earlier disposable candidate receipts are incompatible and cannot be silently migrated or reused. The fixture now uses newly generated test issuer and broker keys and an inactive Node socket-client candidate; it does not connect the actual worker. The client verifies a signed response bound to the request and a fresh nonce, but sends its grant before authenticating the server: a substituted socket can receive that grant. A protected socket path or authenticated handshake before sending credentials, trusted key provisioning, and path-swap tests remain required. There is no production issuer, provisioning, revocation, key rotation, trusted identity mapping or production transport. In particular, signature verification cannot establish that an issuer was entitled to grant access. Recovery after grant expiration must have a separately designed authorized reconciliation path; this candidate deliberately denies expired grants.

The real worker constructs `ingestedAt` at the readiness call and currently has no durable request identity and complete request snapshot for recovery. The inactive `nativeReadinessIntentCandidate.js` experiment stores an exact request before completion after checking a current ingest lease, and can retrieve it after reopening the database through an authorization callback; it rejects changed requests and incomplete intent schema. The callback is only a test seam, the SQLite data and direct writers remain unprotected in production, and neither intent creation nor retrieval is wired to the real worker. A safe transport integration must persist and reuse these exact values before sending; generating a fresh timestamp or request on restart would prevent exact replay and cannot be substituted for an authenticated reconciliation design.

A signed server challenge alone is insufficient to protect the grant: a substituted socket can relay the challenge to the real broker, then capture the cleartext grant after forwarding its proof. The next transport needs an authenticated, encrypted channel established before any grant or request bytes are sent, with a pinned broker identity and a protected socket directory. For example, TLS over a Unix socket can pin an operator-provisioned broker certificate before the client sends credentials; certificate rotation, socket ownership, UID mapping, handshake deadlines and certificate/private-key isolation must be qualified in the actual deployment. A test must capture all bytes received by a substituted socket and verify they contain neither the grant nor the request; it must also exercise a transparent relay, path replacement, wrong certificate, restart and interrupted handshake. No production TLS configuration is included in this proposal.

`nativeReadinessTlsTransportCandidate.js` is now a separate, inactive client experiment using TLS 1.3 over a Unix socket. It pins the SHA-256 digest of the exact peer certificate before sending request or grant bytes; it deliberately does not perform CA, hostname, certificate-expiration or revocation validation, so trusted pin provisioning, lifetime and rotation remain mandatory. Its isolated test uses publicly committed synthetic-only private keys that must never be used outside tests. It exercises a wrong certificate, replacement of a socket endpoint, an interrupted handshake, and an encrypted transparent relay, and verifies the synthetic grant and request are not exposed to those observers. The separate SO_PEERCRED broker fixture now also accepts TLS and signed grants and exercises a lost-reply replay through the pinned client; it does not integrate the real worker or production keys, and does not qualify the deployment topology or real worker restart recovery.

## Readiness contract to implement and qualify

The direct ingest path in `processingWorker.js` constructs an event containing the event ID, schema version, type, project and task identifiers and display names, attempt, requesting subject, status and review URL. It passes that event, the precise attempt and job IDs, the current lease owner and `ingestedAt` to `completeOutputForReview`. That method checks the unexpired job lease, staged output and model/version relationship and commits the ready states, completed job, event outbox entry and audit event together. A broker client must preserve those semantics and the worker's failure handling; substituting the fixture's hard-coded event or lease owner is not equivalent. Optional derivatives are enqueued afterward and their existing failure behavior also needs coverage.

For a candidate protocol, bind the authenticated caller and operation to an immutable request identity and the exact attempt, job, lease credential, ingestion time and complete event payload. Reject unknown fields, malformed data, changed payloads under the same identity, unauthorized attempts and expired or replaced leases. Authenticate the broker endpoint as well as the caller under the actual deployment topology; knowledge of a lease-owner string alone is not sufficient authorization. The broker must check state and authorization at execution, not only when accepting a request. Request and response sizes and deadlines must be bounded; neither input nor errors should expose credentials or private payloads in logs.

Persist the request identity and a canonical digest of its validated payload in the same durable transaction as the actual readiness update, event and audit records. A replay with the identical authorized identity and digest may return the same committed result; a changed request, missing or conflicting receipt, or uncertain crash outcome must hold for reconciliation. Never infer a successful replay merely from an attempt already being ready or a marker existing. A timeout or lost response is unknown, not permission to run a second transition or discard source data. Test transaction rollback, lost reply after commit, restart, duplicate and altered request, lease loss and event/audit equivalence. This is a proposed contract, not an implemented guarantee.

`server/nativeReadinessBrokerCandidate.js` now exercises part of that contract against the actual `completeOutputForReview` method in a single SQLite transaction with a candidate receipt. It is not wired into a worker, listener or migration. Its authorization callback is a test seam, not authentication; its receipt schema and marker remain forgeable by unrestricted database writers. Tests cover transaction rollback on an injected audit failure, lease loss, identical replay after reopening the database, changed requests and event/audit preservation. The candidate attests its exact receipt schema and checks event names against current database records and the review URL against a trusted configuration input. Crash-at-every-boundary, actual peer and tenant authentication, server identity, malformed/partial schema, runtime transport, and full writer fencing still require implementation and independent qualification. The replay guarantee is conditional on the isolated, untampered database assumed by the candidate.

Required derivatives have a separate completion path, `completeDerivativeAndMaybeReady`, with a derivative lease and potentially the final readiness transition. Its exact job token, result and event semantics require an equivalent independently tested contract; routing only the direct ingest method misses that path. Earlier model registration, output staging, attempt updates and derivative scheduling also write directly today. Until every relevant writer and asset path is isolated and migrated, brokering either readiness method alone does not establish trustworthy provenance or permit acknowledgement or cleanup.

Current new ingestion requires a textured OBJ and GLB, so its required mesh derivative normally makes `derivativeWorker` the readiness path. The inactive `nativeDerivativeCompletionCandidate.js` calls the actual `completeDerivativeAndMaybeReady` transaction with the exact job, owner, lease token, result and event, and records an attested-schema replay receipt in the same transaction. Tests exercise final and non-final completions, rollback, event/diagnostic/audit preservation, altered result rejection and a transition-process crash after commit. Its authorization remains a test callback, no production broker implementation connects it to the worker or TLS fixture, and its 64 KiB result bound is not reconciled with the transport's 4 KiB limit. Direct database writers can forge its records, and all earlier derivative registration and filesystem writes still bypass a broker. No production or full worker-restart guarantee follows from this experiment.

An experimental derivative worker injection was removed after review: simply returning on an uncertain broker response left a leased job eligible for ordinary reclaim after expiry, which could regenerate or publish before reconciliation. The inactive `nativeDerivativeIntentCandidate.js` stores an exact request under the current derivative lease. An opt-in repository guard checks intent in the same SQLite transaction before claim or timeout terminalization, holding all derivative jobs for the affected attempt; a fresh repository process test covers expired leases and deadlines. Candidate reconciliation reads the saved request, invokes exact completion/replay and records a separate immutable resolution only after rechecking the corresponding completion receipt and marker. Before allowing later work, the guard independently checks attested schemas, saved request digest and identity, the completed job's result, exact resolution and receipt agreement, and the marker for a final completion. Missing, corrupt or unbacked evidence holds. An expired request without a completion receipt remains held; no new lease or inferred result is fabricated. These checks do not prevent a fully privileged direct writer from fabricating all relevant records.

The worker now offers a separate optional broker injection only when the repository guard is enabled and reconciliation runs before claim. Its completion path calls prepare, verifies the exact returned request, requires a positive confirmation, then calls completion; an uncertain preparation prevents completion. A synthetic restart invokes the real worker entry point against an expired unresolved intent and confirms it does not claim the job; separate in-process tests stage an intent before simulated lost replies. No production configuration creates this broker. The worker relies on its broker to make preparation and confirmation durable and truthful; authenticated transport, issuer authority, timeouts and the implementation's crash ordering still require independent qualification. The tests do not demonstrate an actual TLS-backed derivative run or conversion-process interruption. The default unguarded worker still writes already-ready optional derivatives directly.

A further disposable test runs the actual `processOneDerivative` lane in a child process with a synthetic generator and same-process local broker. Killing that worker after intent preparation, then expiring its lease, leaves the job leased and attempt in derivatives on restart; killing it after completion commit leaves the job complete and attempt ready while restart reconciles the original receipt without invoking the synthetic generator again or duplicating event/audit records. The test retains its temporary state if child exit is uncertain. The synthetic generator registers fake output metadata, so this does not establish derivative byte integrity or descendant-process containment. This test deliberately retains direct worker database write access and does not exercise TLS, production supervision, filesystem isolation or a real converter.

`nativeDerivativeLocalBrokerCandidate.js` is a same-process test candidate that commits the intent before returning preparation, rereads it for confirmation, and refuses completion without an exact stored intent. It performs bounded candidate reconciliation; expired requests without receipts remain held. Tests kill its process before and after preparation and verify that no completion is sent before durable intent. It has no network boundary, real issuer or production configuration; its local authorizers are injected callbacks. When the repository guard is enabled, already-ready optional derivatives, malformed or non-object requests, and jobs with missing attempts are excluded before both claim and timeout terminalization, including after lease expiry; the worker also refuses their existing direct completion path. Their full broker implementation remains absent.

`nativeDerivativeTlsBrokerCandidate.js` adds an inactive pinned TLS client for derivative prepare, confirmation and completion, with a bounded wait for a grant and socket deadline. It signals an abort to a late grant provider and ignores a late result; a provider that ignores the signal can continue running or mutating state, so provider lifetime is not bounded by this client. The derivative test server requires a signed grant bound to the exact action as well as the request; a production server must enforce that action requirement explicitly. An isolated in-process TLS broker test invokes the worker's actual completion function, verifies a synthetic signed grant, commits an intent before confirmation, drops the completion reply after commit, and reconciles one event and audit record. It also rejects a wrong certificate and stalled grant provider.

A second disposable-container test runs that completion function in a fresh synthetic worker UID without database read access, against a separate TLS broker UID that checks `SO_PEERCRED`, action-bound test grants and the durable intent. The broker drops the completion reply, restarts, and a fresh worker process replays the exact synthetic request with no duplicate event or audit. The request ID and test grants are supplied by the test harness, not recovered by a production worker. The fixture uses publicly committed test certificates, and the production signed-grant issuer, cross-process broker, authenticated reconciliation, certificate lifecycle and all-writer/filesystem fencing are not deployed or qualified. The injected reconciliation callback still needs a bounded, authenticated implementation; the transport envelope's 64 KiB limit also permits less than a 64 KiB result once other fields are included.

This is not enabled in the real worker: the guard defaults off, old or direct writers bypass it, production intent creation and authenticated reconciliation are absent, and an unresolved intent may hold an attempt indefinitely. Held attempts are excluded before query limits in both claim and terminalization; an isolated test verifies a later independent job can be claimed behind more than 100 held jobs. The added exact-schema index and resolution table make older disposable intent schemas incompatible; no automatic migration is provided. The tests do not prove full production worker restart, filesystem authority, or machine power loss. Every other write and timeout path needs inventory and migration before any integration; broker authorization, direct-writer isolation, result-size limits and earlier direct writes remain unresolved.

## Migration inventory and release gates

The repository has many direct database writers. `server/index.js` creates the API database and repositories; `server/worker.js` and `workerSupervisor.js` independently open it; repository methods perform SQL directly throughout request, job, audit, session, lifecycle and derivative flows. Some paths described as reads instantiate `ProcessingRepository`, whose constructor seeds presets and therefore writes. The worker Compose healthcheck now uses a read-only SQLite connection instead of the migration-capable `openDatabase`; it must still be qualified against actual WAL/SHM permissions, since a read-only SQLite connection is not proof of filesystem isolation. The supervisor still initializes and performs its SQLite lock preflight. Every such path, scheduled command, maintenance tool and older image must be inventoried and routed through the boundary or removed before denying direct write access. A single-method broker does not run the current app.

An opt-in disposable-container test used distinct synthetic writer and reader UIDs with a private `/tmp`: the reader lacked database and directory write access, read the fresh heartbeat with live WAL/SHM, returned unhealthy for copies missing both sidecars or just SHM, and returned unhealthy during an exclusive lock before recovering after release. This is point-in-time evidence for the tested SQLite build and permissions, not qualification of the installed Viewer image, real UID mappings, production filesystem, WAL recovery or full writer isolation.

Before a staging or production cutover, independently verify all hosts and launch paths, the active mounts and sidecars, service UIDs/groups and capabilities, Docker/Apps restart policies, legacy images, scripts, backups and external writers. Drain and account for active attempts without deleting data. Build and locally test a complete broker contract and client migration; prove unknown methods, wrong principals, stale leases and ambiguous replies hold. Test a separate staging dataset and real topology for WAL locking, crash, ENOSPC, restart, fsync and power loss. Ensure API/worker startup and health checks do not attempt direct writes. Provision and verify OS access and orchestrator enforcement with the operator; a reported environment variable or compose-file intention is not proof. No TrueNAS host command or mutation is included here.

Rollback must retain all accepted operations, commit markers, acknowledgement/outbox records and uncertain files. Do not reconnect an older direct writer or restore an older database snapshot that forgets newer accepted identities. A rollback requires a separately reviewed drain, broker-mediated reconciliation/export compatible with the target version, verified writer exclusion and an operator-controlled cutover. If that cannot be shown, hold the new boundary and data for inspection; do not silently drop tables, disable triggers or prune uncertain artifacts. ACK transmission and cleanup remain disabled until this boundary, coordinator authentication, durable receipt semantics and retention policy are independently qualified.
