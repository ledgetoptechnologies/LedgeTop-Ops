# Employee read gateway prototype

**This is a source-level pilot, not production-qualified file access.** Live
routes remain unmounted. Large-directory pagination, efficient resumable large
transfers and deployment qualification are still required before employee use.

This Linux service is a private, read-only Ops backend. It accepts only signed
`POST /v1/read`; it does not accept desktop credentials, human Access JWTs,
Viewer credentials or MCP keys. Its routes must remain unmounted until the
joined Ops authorization tests and deployment review pass. Nothing here mounts
or contacts the NAS automatically.

The standard-library implementation uses Python 3.14.9, an official patched
maintenance release. Both Dockerfiles use the official
`python:3.14.9-slim-trixie` image. Refresh the supported patched image during
release maintenance; the initial verified manifest digest was
`sha256:a145a961ec2cf5741772d5e39773d979271132884fd778f6c3fad34e52b85402`.

## Explicit enrollment and private configuration

An administrator must enroll each specific source directory from its intended
container mount namespace. Root IDs and increasing generations come from Ops.
Enrollment never discovers directories or changes their contents:

```
python -m employee_read_gateway enroll --root-path /sources/approved-root --root-id 11111111-1111-4111-8111-111111111111 --generation 1
```

Save the returned enrollment object in a private service configuration. Its
fingerprint is SHA256 of UTF-8 lines, with no final newline:

```
ops-employee-root-v1
<rootId>
<generation>
<device>
<inode>
```

Configuration example (replace enrollment values with the actual helper output):

```json
{
  "gatewayId": "22222222-2222-4222-8222-222222222222",
  "keyId": "employee-read-v1",
  "keyFile": "/config/dedicated-signing-key.bin",
  "stateDirectory": "/state",
  "spoolDirectory": "/spool",
  "listenHost": "127.0.0.1",
  "listenPort": 8080,
  "nonceCapacity": 10000,
  "roots": [{
    "root_id": "11111111-1111-4111-8111-111111111111",
    "generation": 1,
    "path": "/sources/approved-root",
    "device": 123,
    "inode": 456,
    "fingerprint": "<helper-generated fingerprint>"
  }]
}
```

The configuration and dedicated binary signing-key file must be regular,
single-link, private files owned by the service user. Their directories, state
and spool must be private (`0700`); files must deny group/other permissions.
The dedicated key must be 32–128 bytes, provisioned separately into Ops and the
gateway. No key is included or generated by this prototype. Source mounts must
be read-only. Only service state and disk-backed temporary spool are writable.

The service defaults to loopback HTTP. An operator-configured TLS reverse proxy
is required for the fixed HTTPS origin used by Ops. Do not expose its HTTP port
publicly. The HTTP adapter has bounded connections, five-second socket I/O,
fixed POST routing, a 16KiB body limit, no request transfer encoding and static
errors. Production TLS, network isolation, ingress header limits, resource
limits, monitoring, key rotation and provisioning still need deployment review.

## Source and resource safety

Each request reopens the enrolled root and checks its device/inode. Traversal
uses Linux directory fds, `O_NOFOLLOW`, nonblocking opens and `fstat`; nested
mount IDs, hard-linked files, symlinks, FIFOs, sockets and special files are
refused. Listing returns at most 200 entries, sorted by UTF-8 bytes. Larger
directories fail explicitly. Paths reject Unicode controls, format characters
and surrogates; private-use Linux filename characters are preserved.

HMAC authenticates exact request bytes. The durable SQLite nonce store claims
nonces transactionally, expires old entries and refuses saturation. Admission
proof is accepted for at most 30 seconds. A separate signed deadline bounds
preparation to at most 15 minutes, no later than the upstream human session's
verified expiry. Ops must recheck the exact human admission and read grant
after this upstream await and before handing off metadata or bytes.

The service hashes a single copy into an unlinked private temporary file, then
serves only that snapshot. It never hashes a live fd and rereads it for content.
Source identity, size, mtime and ctime are compared around copying. Content
always reopens the source and makes a new snapshot; a previous snapshot does
not authorize a deleted or replaced source. Ranges are inclusive, pinned to the
expected SHA256 and checked against the exact snapshot length.

Stat comparisons are a consistency check, not an atomic filesystem snapshot:
same-tick mutations may retain identical timestamps. Concurrent/adversarial
writers can therefore evade stat-change detection. The returned digest still
matches exactly the immutable bytes served. Stronger point-in-time source
semantics require filesystem snapshots or a cooperative finalized-ingest
workflow; this remains a staging qualification gate.

Defaults permit 64GiB files and 128GiB total reserved snapshots, preserve 1GiB
free disk and allow two concurrent snapshots. File, reservation and available
space limits are checked before copying. Copies check cancellation and deadline
each MiB. Temporary snapshots are unlinked, released on completion/disconnect
and forcibly closed after a maximum 30-minute TTL. Every request currently
rebuilds its snapshot, so hashing large files costs extra I/O and temporary disk.
No permanent duplicate raw-photo archive is created.

## Synthetic tests

```
docker build -f Dockerfile.test -t ops-employee-read-gateway:synthetic .
docker run --rm --network none --read-only --tmpfs /tmp:rw,nosuid,nodev,size=256m --cap-drop ALL --security-opt no-new-privileges ops-employee-read-gateway:synthetic
```

All fixture data is created inside the container. No host content or NAS is
mounted. The >30GiB test uses a sparse file and mocked free-space preflight,
cancelling before data copy; it proves bound handling, not throughput. Actual
nested mounts require privileges absent from the unprivileged test container;
the suite explicitly reports that restriction and separately tests mount-ID
mismatch rejection. No privileged test container is required.

## Remaining performance and deployment gates

The 200-entry response bound and 2,000-entry scan bound deliberately fail closed.
Mapping folders commonly contain thousands of photos, so paginated browsing
with version-fenced cursors is required for those real workflows. The current
service also copies and hashes the entire source for every manifest and every
range request. Resuming a 30GiB file therefore repeats that I/O; it is not yet
an efficient large-job downloader. A version-fenced temporary snapshot cache
with explicit preparation/polling is needed before making performance claims.

Cancellation and deadlines are checked between bounded reads. A kernel-stalled
filesystem read cannot be forcibly interrupted by this Python thread alone;
filesystem I/O policy, container watchdogs and fault-injection qualification are
additional deployment gates. No atomic point-in-time filesystem snapshot or
guaranteed large-transfer throughput is claimed by these synthetic tests.
