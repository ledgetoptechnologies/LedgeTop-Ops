# Retained reservation ledger: integration checks

Status: investigation only. The live cache continues to reopen durable reservation records. Synthetic native controls reproduced a stall after one callback wrote a marker and another reopened it; a retained-handle comparison is evidence for a candidate, not proof of product correctness.

The candidate must preserve the existing process-wide exclusive legacy lease, durable reservation records, conservative disk accounting, and exact-identity deletion. Tests must exercise the actual coordinator, not just an independent registry model:

1. `HydrationCacheConcurrency.AcquireAsync` and `Lease.AcquireExclusiveLegacy`: use two coordinators for one canonical root and a separate process. Prove that queued and active work share root state, the lease excludes a legacy process until the last owner drains, and a new owner can reopen the root after teardown. Include cancellation and failed cleanup. Existing `Legacy` and `ActiveReservationExcludesStaleRemoval` cover parts of this without a retained ledger.
2. `PlaceholderHydrationCoordinator.Reserve` and every `ReservedBytes` call: while one source is paused after its durable reservation is flushed, admit a different entry from a second coordinator. Verify its quota calculation includes both active and unknown durable rows, refuses malformed, missing, duplicated, replaced, or uncertain rows, and never reopens an active record. Assert no undercount after overflow, cancellation, quota timeout or a release failure.
3. `RemoveExactStaleReservation`, cache-hit preparation and `EvictVerifiedCacheAsync`: hold an entry after promotion but before reservation release; concurrent same-entry hydration and eviction must not remove its active reservation. Test canceled waiters and later retry. `ActiveReservationExcludesStaleRemoval` checks current entry and lease exclusion; it does not test a new registry.
4. Release by a retained OS handle only after the correct bytes, Windows volume/file ID, file type and directory binding are verified. Keep conservative accounting and quarantine the root when deletion, close or absence is uncertain. Test replacement and rename attempts, wrong identity, failure before disposition and failure after disposition. The ordinary-file `ReservationHandlePrototype` probes these mechanics but is not coordinator integration.
5. After process termination, reacquire the actual interprocess lease and reconstruct reservations from durable records before admitting new work. Preserve unknown or ambiguous records; never treat a lost in-memory map as zero reservations. Use a child process, assert exact record identity and contents, and distinguish abrupt process exit from machine crash. Do not silently delete unrelated files.
6. Verify root ownership and no-reparse path bindings throughout active work and teardown, including directory or ancestor replacement attempts. A held file ID alone does not prove that a name still resolves to that file. Include incompatible existing versions, cross-process quota contention, multi-root isolation and root-state reference lifetime.
7. Run the gated candidate through the Windows native synthetic provider with the known two-reader stall reproducer, timeout-safe evidence and cleanup verification. Then test the explicitly authorized read-only staging folder and connected upgrade separately. Neither synthetic success nor an ordinary file test establishes live sign-in, actual downloads, Keep, Free, or multi-file performance.

8. Cover other callback-written files before attributing a fix to reservation handles. `OwnedExisting` reopens ownership markers for the cache root, scope, entry and reservation directory; `Downloader` also reopens its ownership marker and transfer-state JSON. Test actual coordinator behavior when a first callback creates or updates each item while a second callback needs it. Any retained marker knowledge must stay bound to verified directory and marker identities and detect replacement, type, content and ownership changes. Preserve fail-closed behavior for unknown markers and noncooperating processes.
9. Trace the actual download path independently: `Downloader` currently closes its partial-file write stream before opening a new read stream for SHA-256, then retains that verified stream across promotion. The verification open itself may share the callback-write risk. Cache hits and the `LifetimeQueuedDownloadSource` fallback also open files by path. Test simultaneous cold downloads, cache hits, resumed partials, source fallback and promotion under native callbacks. Any retained stream must still verify the complete bytes and length, retain write/replace exclusion across verification and transfer, check the post-download authorization, and preserve failed or ambiguous partials. Do not infer a stall at any specific one of these calls without a trace.

Until these pass and receive independent review, keep this change behind a non-packagable test gate. Do not install or ship it as a stall fix.
