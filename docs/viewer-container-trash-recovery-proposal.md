# Container trash recovery (draft)

The opt-in `LTDS_CONTAINER_RECOVERY_REGRESSION=1` HTTP test demonstrates that a project trash retry can return success after a dataset moved but its membership insert failed. The current retry excludes already-trashed datasets from its discovery, so the dataset remains a separate trash item. This is a synthetic interruption, not a production-data test.

Create a durable container plan in the same database transaction as the parent archive and trash record, before child effects. Snapshot exact child entity IDs and types, ownership basis, and stable child trash/mutation identities. Preexisting independent trash must remain distinct unless explicitly included by a defined contract. A task's dataset belongs in the plan only when ownership is established; shared datasets must not be moved by another task's plan. Preserve the existing CSV retention check before any destructive transition.

Process planned children idempotently. Bind each resulting child trash record to its planned identity transactionally when metadata trash is created or when a managed storage mutation completes. After a crash, resume from the plan rather than scanning arbitrary historic trash; a completed child without membership can then be associated from its recorded identity. Hold restore, purge and automatic purge of the container and its planned children while the plan is incomplete. Revalidate ownership and lifecycle state, and preserve a clear retryable or inspectable status for conflicts. Old incomplete trash operations without a plan are ambiguous: do not attach unrelated items by timestamps or guess ownership.

Required checks include interruption after parent planning, child intent, filesystem move, database completion, and before membership; repeated recovery; separate workers; shared datasets; unrelated preexisting trash; competing containers; restore and purge during an incomplete plan; and CSV retention with legacy or mixed-version writers. Activation also requires a rollout fence against old processes that bypass the plan. No release or data migration is authorized by this proposal alone.

The current local action prototype intentionally does not take over an active action after a timeout. A synthetic filesystem interruption test verifies that the active restore, its pending child mutation and refusal of an opposing purge survive reopening the database. This is a hold, not recovery. `/usr/bin/flock` is present in the published baseline Viewer image, but presence alone does not prove usable cross-process or cross-host exclusion. Any proposed OS lock must be held by the executor for every filesystem effect, preserve a stable lock identity, release when that executor is known dead, and prevent a suspended executor from resuming after takeover. Its helper lifecycle must not leave orphan processes. Verify filesystem and mount semantics, process termination, stale executors and mixed-version rollout before relying on it; do not use elapsed lease time as proof that an old filesystem operation stopped.

On October 30, an isolated test on the staging host's temporary filesystem used the published Viewer image and `flock -F`: a second process and a second container could not acquire the same lock while its executor ran or was paused; acquisition succeeded after that task-owned executor was killed. All test containers and files were removed. This supports a no-fork executor experiment only on the tested host and mount. It does not prove cross-host or NAS lock semantics, safe file identity under directory replacement, action/child receipt recovery, behavior during image upgrades, or safe old-worker fencing. An executor must retain the same locked inode through every effect and avoid a separate helper whose unexpected death releases the lock while work continues.

The unwired executor experiment additionally checks `/proc/locks` for its own PID and matching device/inode, and binds the action to a file nonce as well as device/inode. Seven focused tests passed on the staging temporary filesystem, including an open but unlocked matching descriptor and a replaced lock file. This is a point-in-time observation, not a fence: `/proc/locks` does not identify which open file description holds the lock, prove the lock remains held through effects, prevent same-UID replacement or nonce copying, or establish cross-host behavior. Before wiring it to recovery, verify actual mount and PID namespace behavior, maintain exclusive ownership through every effect and recovery step, fence legacy executors, and cover lock release, unlinked descriptors, process death, descendants and interrupted effects. Fail closed when lock visibility or identity cannot be established.

The existing `processing-overview.test.js` restore case initially failed on this local prototype because it directly restored project metadata while the newly created trash plan was incomplete. A new signed overview lifecycle test failed for the same reason; both passed against draft Viewer head `08e6ff81` before the local prototype. The tests now use temporary managed storage and the complete project trash/restore path. All four overview tests pass on the local prototype, including signed failure, recycle, restore and retry. This is synthetic and does not qualify crash recovery or production mounts; do not remove the incomplete-plan guard to permit direct metadata restoration.
