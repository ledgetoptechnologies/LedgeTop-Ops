# Manual staging test: pre-install evidence policy

This is a proposal for review, not an authorization to change an installer receipt, bypass the existing gate, distribute a build, or enable updates. The unqualified connected payload builder continues to emit `freshGenerationStagingQualified=false`. The existing installer builder must continue to reject that receipt until a separately reviewed, exact-payload eligibility mechanism exists.

For a concrete manual staging test, bind one evidence set to the exact commit, Windows source tree, Git source archive, four-part version, unqualified build receipt, canonical inventory, application bytes, SDK host, builder, helper and restore source. Preserve the original build receipt and source/archive and retain the actual test logs. Record the expected Windows staging-only employee scope and disabled updater, and review installer/cleanup and recovery risks. Do not include credentials or client data.

Obtain two distinct independent review records: one for `source-scope` and one for `safety-and-tests`. Each record identifies a reviewer other than the declared builder, states its bounded findings and test results, and is hashed. Reviewer names and outcomes are supplied assertions, not authenticated identities or independent verification by a script. A reviewer must inspect the records and exact artifacts before any manual decision; this file does not make that decision.

Run the existing `windows-pilot-evidence-verify.ps1` against the exact unqualified output first. Then run `windows-pilot-preinstall-verify.ps1` against the existing verifier manifest, a separate review manifest and the review records. It checks byte pins, stated review separation and exact build metadata; it does not prove who authored a record, that a review was adequate, that the payload arose from the source archive, or that a build is eligible. Never represent its result as a qualification receipt or use it to set the existing flag.

These are path-based checks with check-then-use windows, not an atomic snapshot. Use trusted, stable local inputs and prevent concurrent modification; do not treat a successful result as protection against another process replacing files during the check. Git and the base verifier must also be trusted local tools.

The review manifest is JSON with `schemaVersion: 1`, `baseManifestSha256`, the 40-character `sourceTree`, `builderIdentity`, and exactly two `reviews` entries. Each entry has `kind`, `reviewer`, a leaf JSON `file` in the separately supplied review directory, and its `sha256`. The kinds are `source-scope` and `safety-and-tests`; reviewer labels must differ from one another and from the declared builder. Each review JSON repeats its `kind` and `reviewer`, `result: "pass"`, a nonempty `findings` summary, and the exact `sourceCommit`, `sourceTree`, `sourceArchiveSha256`, `version`, `receiptSha256`, `inventorySha256`, `applicationSha256`, `builderSha256`, `dotnetSha256`, `helperSha256`, `sdk`, `restoreSource`, and `syntheticTestEvidenceSha256`. The last hash must identify a `synthetic` evidence entry in the base manifest. These fields are assertions for a person to review, not signatures.

Invoke the wrapper with `-ManifestPath` for the existing byte-verifier manifest, `-ReviewManifestPath`, `-ReviewDirectory`, `-BuildRoot`, and `-SourceRepository`. Keep detailed review findings in separately retained evidence; the compact records alone cannot establish their substance.

Keep evidence labels separate: `pre-install` means source, construction and synthetic checks only; `installed` requires actual install/upgrade behavior; `connected-live` requires the corresponding real authenticated operation. Missing later evidence remains unverified. The next step after independent review is a separate, reviewed implementation of any narrowly scoped gate or promotion mechanism; do not manually edit the receipt to satisfy the current gate.
